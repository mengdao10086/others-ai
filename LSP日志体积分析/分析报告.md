### 9.3 2,136 条「状态观测」的源码位置与高频原因

- 输出语句：`MainHook.java:732`，位于方法 `observeConnectState(int st, boolean scanning)`（`MainHook.java:724`）。
- 调用链：tick 线程每秒循环（`MainHook.java:486` 的 `Thread.sleep(1000)`）→ `if (!bleConnected)`（`MainHook.java:472`）→ `maybeClearStuckControllerState()`（`MainHook.java:473`）→ `observeConnectState(...)`（`MainHook.java:702`）→ `XposedBridge.log(...)`（`MainHook.java:732`）。
- 节流：`STATE_OBS_LOG_INTERVAL_MS = 30 * 1000`（`MainHook.java:187`），即最多 2 条/分钟；没有「仅在 state 变化时打印」的判断（`MainHook.java:730` 只判断距上次输出是否满 30s）。

**为什么是 2,136 条**：日志跨度 24.27 小时，按 30s 一条理论上限约 2,913 条；实际 2,136 条，占理论上限 73.33%，相当于累计约 17.80 小时处于「App 侧 `bleConnected=false` 且控制器可读」的状态。也就是说，日志期间 App 大部分时间认为 BLE 未连接，这个 30s 观测器就一直在跑；它不是 5 分钟限频的重连心跳，而是专门用来诊断 state 卡死的观测，因此成为体积第一的来源。

- 2,136 条 = 575,038 B，占模块 68.32%、占全日志 40.46%。
- state 分布：state=0 776 条 / 209,117 B（36.33%）；state=1 1,360 条 / 365,921 B（63.67%）。
- 其中 state=1 有 1,360 条（63.67%），而调用前提是 `!bleConnected`：App 侧标记为断连时，SDK 控制器仍大量时间报告 state=1（连接中/已连接），这正是该观测想捕捉的「门禁状态不一致」，也说明日志不是异常噪声而是诊断输出。

**降体积建议**（与第 8 章一致，这里给出精确改法）：把 `MainHook.java:732` 的输出条件从「每 30s 无条件」改为「`st != lastObservedState` 时输出一条，另每 5 分钟补一条心跳」；或把 `STATE_OBS_LOG_INTERVAL_MS` 提到 5 分钟。本日志 2,136 条里 state 只发生 289 次变化，按变化打印只会保留 289 条左右的样本，省掉大部分 575,038 B，同时不丢失关键诊断信息。

数据来源：`base.apk`（包名 `com.sevtinge.hyperceiler`，版本 `2.10.166-20260331`）的 baksmali 反编译结果；日志侧按「一条 E 级业务消息 + 其续行 + 紧随的带头部堆栈帧记录」重建异常单元。

异常完整文本：`java.lang.IllegalStateException: Reject hook registration for public void android.widget.Toast.show(): callback class class k2 already registered 64 times`。

### 10.2 逐类解释与代码对应

**这条异常是什么**：它不是 systemui 业务代码抛出的异常，也不是 HyperCeiler 主动抛错，而是 LSPosed 的 hook 注册器在「同一个回调类已注册 64 次」时拒绝继续注册并抛出的 `IllegalStateException`。异常文本不在 HyperCeiler APK 的 dex 里，`s0`/`l0` 在 APK 中也只是空壳类（实现由 LSPosed 运行时提供），所以抛出点本身无法映射到 HyperCeiler 源码。

**是谁触发的（已对应到代码）**：

1. 规则类 `com.sevtinge.hyperceiler.libhook.rules.systemui.lockscreen.DisableUnlockByBleToast` 在 SystemUI 的规则表中注册：`D:/下载/Claude Code/杂项/LSP日志体积分析/smali/com/sevtinge/hyperceiler/libhook/app/SystemUI/SystemUIB.smali:445-447` 与 `.../SystemUIV.smali:531-533`（由偏好开关 `Lf60;->e(String,Z)Z` 控制）。
2. 它的 `init()` 先注册外层回调 `$2`（日志外层栈显示被 hook 的运行时方法是 `android.hardware.FumpCashBeland.makeText`）；`$2.before` 每次 makeText 时再注册一个 `Toast.makeText(Context,int,int)` hook `$2$1`（`D:/下载/Claude Code/杂项/LSP日志体积分析/smali/com/sevtinge/hyperceiler/libhook/rules/systemui/lockscreen/DisableUnlockByBleToast$2.smali:43-68`）。
3. `$2$1.before` 取出 makeText 的资源 ID，匹配到蓝牙解锁提示文案后，又调用 `findAndHookMethod(Toast.class, "show", $2$1$1)`（`...DisableUnlockByBleToast$2$1.smali:80-110`）。也就是说：**每发生一次匹配的 Toast.makeText，就新增一个 makeText hook，而每个 makeText hook 回调又往 Toast.show 上再挂一个 hook**，两层都没有去重/幂等判断，show 层增长更快。
4. 第 64 次之后 LSPosed 拒绝注册 → 本次 `findAndHookMethod` 抛错 → `EzxHookHelper` 打印整条堆栈。异常里的 `k2` 在 APK 中是 synthetic lambda 类（`smali/k2.smali`），`$2$1$1.before` 本身只是 `setResult(null)` 用于吞掉 Toast（`...$2$1$1.smali:37-42`）。
5. 日志外层栈还给出触发场景：`MiuiBleUnlockHelper.tryUnlockByBle` → `setBleUnlockState` → `bleListener$1.onUnlocked` → `MiBleUnlockProfile$1.notifyProperty` → Handler → `android.hardware.FumpCashBeland.makeText`，全在 systemui 主线程。即每次蓝牙解锁事件触发解锁提示 Toast 时，这条自增殖 hook 链就继续增长。

**因此对应的 HyperCeiler 功能是「禁用蓝牙解锁 Toast」规则**（`DisableUnlockByBleToast`），不是随机的系统异常。`$1$1.before` 那条同构路径只出现 1 次，属于同一规则的另一分支。

### 10.3 偶发还是必现

**条件必现**：只要该规则开启、蓝牙解锁反复弹出对应 Toast，每次 makeText 都会新增一个 `Toast.show` hook；累计到 64 次后，后续每一次匹配的 makeText 都会抛这个异常并打印堆栈。日志里表现为两簇：
- `2026-10-31T18:40`：10 次 / 200,260 B（纯堆栈 198,257 B）。
- `2026-10-31T19:07`：22 次 / 286,142 B（纯堆栈 281,720 B）。
- 单条体积在 3,576–24,024 B 之间，且同一簇内递增（18:40 簇 16,000→24,024 B；19:07 簇 3,576→22,494 B）：每多挂一个 hook，异常堆栈就多穿一层调用链，所以越到后面日志越大。这不是随机丢帧，而是 hook 链长度在增长。

### 10.4 实际影响：噪音还是有实际影响

- **不是 systemui 崩溃/重启的原因**：日志跨度内 `com.android.systemui` 的 pid 始终是 4916（185 条记录），没有 `FATAL EXCEPTION`、`ANR in`、`has died`、`Watchdog`、`Force finishing` 等记录（均为 0 次）。
- **有实际功能影响**：规则在累计 64 次后无法再注册新的 `Toast.show` hook，「禁用蓝牙解锁 Toast」在新 Toast 上失效；已注册的 64 个 hook 仍挂在 `Toast.show` 上，之后每次 Toast 都会穿过更长的 hook 链，增加 systemui 主线程开销。
- **日志/性能影响**：每次匹配的解锁 Toast 都在主线程生成 3.6–24 KB 的异常堆栈并写 LSPosed 日志；本次日志中 32 次共 486,402 B（纯堆栈 479,977 B），是 systemui 体积的 99.60%。属于「解锁瞬间的局部卡顿 + 日志膨胀」，没有证据表明会造成 systemui 持续卡顿或重启。
- **结论**：是 HyperCeiler 的功能性 bug（hook 自增殖），不是 systemui 自身异常；建议关闭/修复该规则，或把 `Toast.show` hook 改成进程内只注册一次。
