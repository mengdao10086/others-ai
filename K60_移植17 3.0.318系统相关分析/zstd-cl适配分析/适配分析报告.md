## 一、一句话结论

**不能装；四选一判定为「根本不适配」。**

这个模块自带的是给 **6.18.21-android17** 内核编译的 `zstd_cl.ko`，本机内核是 **5.10.257-android12-9**。三道硬性关卡依次否决：

1. `module_layout` 的 MODVERSIONS CRC 不同（模块 `0x60801db3`，本机 vendor_dlkm 全部模块 `0x2db3247c`）。`check_modstruct_version()` 在符号解析之前执行，失败直接 `-ENOEXEC`（v5.10 `kernel/module.c:3864`）。
2. 即使绕过上一条，模块的 29 个导入符号中有 **13 个**在本机内核镜像里完全不存在，`insmod` 会以 `Unknown symbol` 失败。
3. 模块的注入机制依赖 6.18 的 zcomp 架构（kretprobe `lookup_backend_ops` / `algorithm_params_store`），本机 zram 是 5.10 的 Qualcomm zcomp 实现，这两个函数不存在。

**另有一条独立结论**：本机 zram 已经能选 `zstd`（crypto zstd 后端 + `zram.ko` 的 4 个后端里有 zstd），压缩等级固定为 3。也就是说，模块要补的「系统没有 zstd」在本机不成立；它唯一多出的「可调 level」在这个 5.10 内核上没法由这个 `.ko` 提供。

## 四、关键判据逐项比对

| 判据 | 模块侧 | 本机内核侧 | 结论 |
|---|---|---|---|
| 架构 | aarch64 ELF64 | aarch64 | 过 |
| 页大小 | vermagic 标 `-4k` | `CONFIG_ARM64_4K_PAGES=y` | 过 |
| `CONFIG_MODULES` | 需要外部模块 | `y` | **过** |
| `CONFIG_MODULE_SIG` / `MODULE_SIG_FORCE` | 无签名（也不需要） | `# CONFIG_MODULE_SIG is not set` → 不启用签名校验 | **过**（签名不是卡点） |
| vermagic | `6.18.21-...-4k SMP preempt mod_unload modversions aarch64` | `5.10.257-... SMP preempt mod_unload modversions aarch64` | **过**（见下） |
| `module_layout` CRC | `0x60801db3` | 本机 vendor 模块统一 `0x2db3247c` | **不过** |
| 导入符号 | 29 个 | 13 个不存在 | **不过** |
| 符号 CRC 逐项 | `__versions` 内有 28 条 | 无法从 raw Image 取出 `__kcrctab` | **未验证**（被前两项否决，无需继续） |
| zcomp 注入接口 | `lookup_backend_ops` / `algorithm_params_store` | 两名称在内核与 `zram.ko` 中均 0 命中 | **不过** |
| KMI / 内核代际 | 6.18 / android17 | 5.10 / android12-9 | 不过（KMI 不通用） |

### 4.1 vermagic 为什么「过」

模块与内核都开了 `CONFIG_MODVERSIONS`，且模块带 `.modinfo` 之外的 `__versions` CRC 表。v5.10 `kernel/module.c:1369-1375` 的 `same_magic()` 明确写着：

```c
/* First part is kernel version, which we ignore if module has crcs. */
static inline int same_magic(const char *amagic, const char *bmagic, bool has_crcs)
{
	if (has_crcs) {
		amagic += strcspn(amagic, " ");
		bmagic += strcspn(bmagic, " ");
	}
	return strcmp(amagic, bmagic) == 0;
}
```

```c
} else if (!same_magic(modmagic, vermagic, info->index.vers)) {   // module.c:3160
```

两侧首个空格后的字符串完全相同：

```
SMP preempt mod_unload modversions aarch64
```

所以 vermagic **不拦**。这一点容易被误判成「版本不同就装不了」，实际真正的拦截在下一步。

### 4.2 `module_layout` CRC 为什么「不过」

模块 `__versions` 中 `module_layout` 的 CRC 是 `0x60801db3`。本机 `vendor_dlkm` 中 4 个抽样模块（zram.ko、zsmalloc.ko、lzo.ko、qca_cld3_qca6490.ko）全部是 `0x2db3247c`，268 条 vermagic 全部是 `5.10.160-gki-*`。

v5.10 `kernel/module.c:3863-3867`：

```c
/* Check module struct version now, before we try to use module. */
if (!check_modstruct_version(info, info->mod)) {
	err = -ENOEXEC;
	goto free_copy;
}
```

本机系统运行依赖 vendor_dlkm 的模块（`modules.load` 第 2/3/4/95 行即为 zsmalloc/lzo/lzo-rle/zram），这些模块的 `module_layout` CRC 全部是 `0x2db3247c`；模块的 `0x60801db3` 与它们不一致，会在符号解析之前被判 `-ENOEXEC`。

> 内核镜像里的 `__kcrctab` 精确值没有直接取出（raw Image 无节表），这一条以「本机 vendor 模块 CRC 一致且系统依赖其加载」为依据；缺失的取证见 §七。

### 4.3 符号依赖为什么「不过」

13 个导入符号在本机内核镜像中 0 命中（§2.4 列表）。内核即便通过了 CRC 检查，`resolve_symbol()` 也会因 `Unknown symbol zstd_create_cctx_advanced (err -2)` 拒绝加载。

### 4.4 zcomp 注入接口为什么「不过」

- 内核 Image：`lookup_backend_ops` 0 命中、`algorithm_params_store` 0 命中。
- 本机 `vendor_dlkm/vendor_dlkm_a/lib/modules/zram.ko`（127296 B，5.10.160-gki）：`lookup_backend_ops` 0 命中、`algorithm_params_store` 0 命中；只有 `zcomp_available_show`、`comp_algorithm_show/store`、`zcomp_create` 等 5.10 接口。
- 模块的 `init_module` 要求三个 kretprobe 全部注册成功，任一失败即整体失败。

## 五、系统侧现状：这台机器缺不缺 zstd

### 5.1 zram 由 vendor 模块提供

`分区/` 由 `super.img` 切出（`manifest.json` 的 `image` 字段指向 `...\images\super.img`）。`vendor_dlkm_a.img` 为 EROFS（magic `e2e1f5e0` @1024），用 `extract.erofs.exe` 展开后：

- `vendor_dlkm_a/lib/modules/zram.ko`（127296 B）
- `vendor_dlkm_a/lib/modules/zsmalloc.ko`（78792 B）
- 两者的 `.modinfo`：`vermagic=5.10.160-gki-gf555d54c041a SMP preempt mod_unload modversions aarch64`，`intree=Y`，`zram.ko` 的 `depends=zsmalloc`。

加载清单 `vendor_dlkm_a/lib/modules/modules.load`：

```
2:zsmalloc.ko
3:lzo.ko
4:lzo-rle.ko
95:zram.ko
```

`modules.dep`：`/vendor/lib/modules/zram.ko: /vendor/lib/modules/zsmalloc.ko`。

### 5.2 这个 zram 已经支持 zstd

`zram.ko` 的 `zcomp_available_show` 反汇编（`llvm-objdump -dr`）依次用 4 个名字做 `strcmp`：

| 重定位 | `.rodata` 实际字符串 |
|---|---|
| `.rodata+0x3e5` | `lzo` |
| `.rodata+0x21e` | `lzo-rle` |
| `.rodata+0x29c` | `lz4` |
| `.rodata+0x4c2` | `zstd` |

`zcomp_available_algorithm` 与 `zcomp_create` 都调用 `crypto_has_alg(name, 2, 0xf)`（`CRYPTO_ALG_TYPE_COMPRESS = 0x2`，`CRYPTO_ALG_TYPE_MASK = 0xf`，见 v5.10 `include/linux/crypto.h:39-46`）。

内核 `CONFIG_CRYPTO_ZSTD=y`。v5.10 `crypto/zstd.c` 同时注册了两个算法：

```c
static struct crypto_alg alg = {
	.cra_name		= "zstd",
	.cra_driver_name	= "zstd-generic",
	.cra_flags		= CRYPTO_ALG_TYPE_COMPRESS,
	...
static struct scomp_alg scomp = {
	.base = { .cra_name = "zstd", .cra_driver_name = "zstd-scomp", ... }
```

即 `crypto_has_alg("zstd", 2, 0xf)` 可以命中 comp 类型，`zram` 的 zstd 后端可用。

`comp_algorithm_store` 反汇编（0x3c2c–0x3cf4）显示它只做 `crypto_has_alg(name, 2, 0xf)` 检查，通过后直接 `strcpy` 到 zram 的 compressor 字段，**没有算法白名单**。所以：

- `echo zstd > /sys/block/zram0/comp_algorithm` 可以被接受；
- 任何注册为 comp 类型、名字任意的 crypto 算法也会被接受（这对 §六 的替代方案有用）。

压缩等级：v5.10 `crypto/zstd.c` 的 `ZSTD_DEF_LEVEL 3`，`params = ZSTD_getParams(3, 0, 0)`，等级写死为 3，没有 sysfs 调级接口。

### 5.3 zram 何时建立

- `vendor/etc/init/hw/init.qti.kernel.rc:170-177`：`on property:sys.boot_completed=1` → `start kernel-boot`、`start kernel-post-boot`。
- `vendor/etc/init/hw/init.qcom.rc:754-757`：`on property:sys.boot_completed=1` → `start qcom-post-boot`。
- `vendor/bin/init.kernel.post_boot.sh:33-78` 的 `configure_zram_parameters()`：按 MemTotal 设 disksize（>2 GB 取 50%，上限 4096 MB）、`mkswap /dev/block/zram0`、`swapon -p 32758`；`:132` 无条件调用。
- `vendor/bin/init.qcom.post_boot.sh:584-631` 同逻辑，`:711`（msmnile/kona/sdmshrike 分支）与 `:826`（其他机型分支）都调用。
- `vendor/etc/fstab.qcom` 中**没有** zram/swap 行；`vendor/etc/fstab.default` 不存在，`system_ext/etc/init/perfservice.rc:14` 的 `swapon_all /vendor/etc/fstab.default` 落空。zram 由上述 post_boot 脚本建立。
- `product/etc/build.prop:88`：`vendor.zram.disable=1`（同一行邻近 `ro.build.version.incremental=OS3.0.318.0.WPCCNXM`）。在已展开的 system/system_ext/product/odm/mi_ext 文本树中检索该属性，只有定义处，**没有文本消费者**。
- `system/etc/init/hw/init.rc:1373-1403` 对 `/sys/block/zram0/{idle,writeback,new,mfz_enable,...}` 做 chown/chmod，说明系统按「zram0 存在」设计。

### 5.4 结论

本机 zram 的算法集合是 `lzo / lzo-rle / lz4 / zstd`，zstd 已经可用，等级固定 3。模块宣传的「系统没有自带 zstd 压缩算法」在本机不成立；`zstd-cl` 的唯一增量是「可调 level」，而这个增量需要 6.18 zcomp，本机没有。

## 六、若要强行适配，需要做什么，代价多大

按代价从低到高：

1. **只想要 zstd（不调级）——零代码**
   在 zram 初始化前（`boot_completed` 之前）或重置后写入：
   ```
   swapoff /dev/block/zram0        # 若已 swapon
   echo 1 > /sys/block/zram0/reset
   echo zstd > /sys/block/zram0/comp_algorithm
   ```
   之后由 `configure_zram_parameters` 设 disksize/mkswap/swapon。等级固定 3。前提是 `zram.ko` 能在本内核加载（见 §七 第 1 条）。

2. **想要可调 level —— 新写一个 5.10 模块（不是「重编」本模块）**
   本包只有 `.ko`，没有源码；它的实现绑定 6.18 的 `zstd_create_*_advanced` / cdict/ddict 与 zcomp 注入点。可行路径是另写一个 5.10 crypto comp 驱动：
   - `crypto_register_alg()` 注册 `cra_name = "zstd-cl"`、`cra_flags = CRYPTO_ALG_TYPE_COMPRESS`；
   - 用本机已导出的旧 zstd API（`zstd_init_cctx`、`zstd_compress_cctx`、`zstd_get_params`、`zstd_cctx_workspace_bound`、`zstd_is_error`，均在 Image 中命中）实现 compress/decompress；
   - 模块参数 `level`，在 `cra_init` 时读取；
   - 依赖 `comp_algorithm_store` 无白名单的行为（§5.2 已证），`echo zstd-cl > comp_algorithm` 即可被接受。
   代价：需要与本机 5.10.257 定制内核匹配的头文件/`Module.symvers`（端口内核源码是否公开未查，见 §七）；模块 `module_layout` CRC 必须由该内核构建产生；约 200–400 行代码 + 真机验证。GPL 符号（`crypto_register_alg` 为导出符号，Image 中命中）。

3. **重编内核把 zram/zstd-cl 内建 —— 不必要**
   本机 zram 已由 `zram.ko` 提供，zstd 已在 crypto 层内建；重编内核不能解决模块的 6.18 API 问题，只会扩大改动面。

4. **给 6.18 模块打补丁 —— 不可行**
   无源码；`__versions` 里 28 条 CRC 全部来自 6.18 构建，任何一条与 5.10 不同都会被 `check_version()` 拒绝；且 13 个符号在 5.10 没有对应实现，需要重写压缩路径。等价于第 2 条。

签名不是障碍（`CONFIG_MODULE_SIG` 未开），`bootloader` 解锁状态不影响本次判断。

## 七、未验证项

1. **设备上 zram0 的实际状态**：`/sys/block/zram0/comp_algorithm`、`disksize`、是否已 swapon、`zram.ko` 是否真的加载成功。本次为纯离线分析，未连接设备，无法读取运行态。缺的设备证据：`cat /proc/modules | grep zram`、`cat /sys/block/zram0/comp_algorithm`、`cat /proc/swaps`。
2. **内核 `__kcrctab` 中 `module_layout` 的精确值**：raw Image 无 ELF 节表，未能定位 `__kcrctab` 段起点。§4.2 用「本机 vendor 模块 CRC 全为 `0x2db3247c` 且系统依赖其加载」推定；要坐实需要该内核的 `Module.symvers` 或 `vmlinux`。
3. **`zram.ko` 的默认压缩算法**（`CONFIG_ZRAM_DEF_COMP`）：模块二进制里 `lzo`、`lzo-rle`、`lz4`、`zstd` 四个名字都在，无法从字符串唯一确定编译期默认值。不影响结论。
4. **`vendor.zram.disable=1` 的消费方**：已展开的文本树中无消费者；framework jar 内部未检索。该属性是否导致 zram 被上层跳过，未验证。
5. **本机 5.10.257 端口内核源码可用性**：未查。决定 §六 第 2 条是否可落地。
6. **`zstd_cl.ko` 的逐符号 CRC 对照**：未做（`__versions` 有 28 条，内核侧 CRC 表取不到）。被符号缺失与 `module_layout` 先行否决。
