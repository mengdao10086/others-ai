## 一、结论（先看这里）

1. 「应用单独设置」这个开关**只控制 MIUI 的 Force Dark（画布级反色）**，不控制应用的原生深色（`values-night`）资源，也不改变应用的 `uiMode`。证据：全 ROM 中 `getAppDarkModeEnable` 的唯一消费者是 `android.view.ForceDarkHelperStubImpl`（`miui-framework.jar`），`services.jar` / `SystemUI` / `Settings` 均无其它消费者；开关写入路径见 §3.1。
2. 这套判定是**进程级缓存**：应用进程启动时读一次「是否深色 / 本应用开关 / 名单 origin / 每应用配置 / 原生深色支持」，之后只有「本应用开关变化」会通过 Binder 观察者推回进程；名单、配置、origin、原生判定在进程生命周期内不再刷新。证据见 §3.2。
3. 所以「有时生效、有时不生效」不是随机，而是由**进程何时启动、切换开关时进程有没有已注册的观察者、以及该应用命中了哪条静态规则**三者共同决定。逐条见 §四。
4. 单个应用内部「有的页面生效、有的不生效」是独立的一层：每应用 JSON 里有 **Activity 级**与**View 级**反色开关，当前 ROM 的 47 个可配置应用里共有 **363 条 Activity 规则，其中 29 条显式 `forceDark:false`**；WebView 还有单独的「黑罩」处理。证据见 §3.5、§3.7。
5. 对「开关能打开、但完全没效果」的应用，最典型的三种静态原因是：
   - 应用被每应用配置写成 `forceDark:false`（黑名单，优先于用户开关）：本 ROM 共 30 个，含微信、QQ、QQ 音乐、网易云音乐、WPS、知乎、拼多多、爱奇艺、优酷、UC、高德等（§3.5）。
   - 应用不在名单里（`forceDarkOrigin=true`）：MIUI 完全不接管，开关对它没有意义（§3.4）。
   - 名单内但没有任何 `<pkg>.json` 配置：只能落到主题属性 / 原生深色支持判定，判定失败就不生效（§3.6）。
6. **具体案例**：`com.flydigi.waspwing.experimental` 在本地名单/配置中完全不存在 ⇒ 只能来自云名单；其冷启动一黑一白的最可能输入是「进程并非真冷」「云名单/云配置异步或竞态」「Binder 静默降级」；验证命令见 **§四·补充（§4.9）**。

## 三、机制拆解（逐条带证据）

### 3.1 设置页的开关怎么写进系统

`Settings.apk` → `com.android.settings.display.DarkModeFragment`：
- 列表数据来自 `DarkModeAppCacheManager.getDarkModeAppInfoList()`，通过 Binder transaction **16777210** 向 `uimode` 服务取 `DarkModeAppData`（`ForceDarkUiModeModeManager.onTransact` case 16777210）。
- 用户拨动开关 → `onAppChecked()` → `DarkModeAppCacheManager.setAppDarkMode(pkg, enable)` → Binder transaction **16777214**，参数 `(packageName, boolean, userId=0)`。
- **没有**强杀、重启或广播应用的逻辑（仅对淘宝额外发一个 `com.taobao.taobao.switch.status` 广播）。

证据：
- `反编译\settings-com.android.settings.display.DarkModeFragment.java`，方法 `onAppChecked`
- `反编译\settings-DarkModeAppCacheManager.java`，方法 `setAppDarkMode`
- `反编译\miui-services-full\sources\com\android\server\ForceDarkUiModeModeManager.java`，`onTransact` case 16777210 / 16777214

服务端落库：
- `ForceDarkAppListManager.setAppDarkModeEnable()`：写 `Settings.System "last_app_dark_mode_pkg" = pkg:enable`，再 `SecurityManagerInternal.setAppDarkModeForUser()` → `SecurityPackageSettings.isDarkModeChecked`，随安全中心设置 XML 持久化。
- 通知：只遍历 `RemoteCallbackList<IAppDarkModeObserver>`，对 **packageName 相同**的已注册进程回调 `onAppDarkModeChanged(enable)`。

证据：`反编译\miui-services-full\sources\com\android\server\ForceDarkAppListManager.java`；`...\ForceDarkUiModeModeManager.java`，方法 `setAppDarkModeEnable` / `registerAppDarkModeCallback`；`...\com\miui\server\SecurityManagerService.java`，`setAppDarkModeForUser` / `getAppDarkModeForUser`。

### 3.2 应用进程怎么读、怎么缓存（核心）

应用进程启动时 `ActivityThreadImpl.miuiFeatureInit()` 调 `ForceDarkHelperStub.getInstance().initialize(appContext)`，**每个进程只初始化一次**。`initialize()` 一次性固定这些字段：

| 字段 | 来源 | 后续是否刷新 |
|---|---|---|
| `mIsDarkModeEnabled` | 当前 `Configuration.uiMode & 48 == 32` | 仅 `onConfigurationChanged` 时刷新 |
| `mIsAppDarkModeEnable` | Binder 16777213 → 服务端 DB/名单 | 仅收到 `onAppDarkModeChanged` 时刷新 |
| `mForceDarkOrigin` | meta-data `force_dark_google` 或 Binder 16777209 | **从不刷新** |
| `mForceDarkAppConfig` | Binder 16777211 → 云配置/`<pkg>.json` | 仅 `onForceDarkConfigChanged`（见下，实际不达 app 进程） |
| `mIsBlackAppDarkMode` / `mIsWhiteAppDarkMode` | 由 `mForceDarkAppConfig.forceDark` 取反/取值 | **配置变化时不重算** |
| `mIsDarkModeSupported` | `AssetManager.isDarkModeSupported()`（原生） | 从不刷新 |
| `mInterceptRelaunchType` | Binder 16777208 | 从不刷新 |

观察者注册点：`ViewRootImpl` 构造函数里 `ForceDarkHelperStub.getInstance().registerAppDarkModeObserver(this.mContext)`。也就是说——**进程必须先创建过一个窗口，才会注册开关变化的观察者**。注册跳过的条件：

```java
if ((this.mForceDarkOrigin && !isSystemUiProcess(pkg))
        || this.mAppDarkModeObserverRegisted || context == null) return;
```

即：`mForceDarkOrigin == true` 的进程永远不注册；注册过一次后不再注册。
开关变化回调只改一个字段并刷新窗口：

```java
public void onAppDarkModeChanged(boolean enable) {
    mIsAppDarkModeEnable = enable;
    refreshForceDarkMode(false);   // 只刷新 mAppVisible 的窗口
}
```

`refreshForceDarkMode()` 遍历 `WindowManagerGlobal.getWindowViews()`，条件包含 `view.mAttachInfo.mViewRootImpl.mAppVisible`，不可见窗口直接跳过；下次可见时由 `ViewRootImpl.handleAppVisibility()` 补一次 `updateForceDarkMode()`。

证据：
- `反编译\miui-framework\sources\android\view\ForceDarkHelperStubImpl.java`（`initialize` / `onAppDarkModeChanged` / `refreshForceDarkMode` / `registerAppDarkModeObserver`）
- `反编译\miui-framework\sources\android\app\ActivityThreadImpl.java`（`miuiFeatureInit`）
- `反编译\framework-selected\ViewRootImpl.java`（构造函数注册观察者；`handleAppVisibility` / `updateConfiguration` / `enableHardwareAcceleration` 调 `updateForceDarkMode`）

### 3.3 最终判定链（`updateForceDarkMode`）

`ViewRootImpl` 在窗口创建/可见性变化/配置变化时先问 MIUI：

```java
if (!ForceDarkHelperStub.getInstance().updateForceDarkMode(this)) {
    updateForceDarkMode();   // AOSP 兜底（见 §3.9）
}
```

MIUI 侧判定顺序（任一命中即返回）：

1. `mForceDarkOrigin` 或 `viewRootImpl == null` → 返回 false（交给 AOSP 兜底）
2. 输入法进程（包名含 `.inputmethod` / `baidu.input` / `com.tencent.qqpinyin`）→ 关
3. `!mIsDarkModeEnabled`（系统不在深色）→ 关
4. `!mIsAppDarkModeEnable`（本应用开关关）→ 关
5. `mIsBlackAppDarkMode`（每应用配置 `forceDark:false`）→ 关
6. `mIsWhiteAppDarkMode`（每应用配置 `forceDark:true`）→ 开
7. 系统应用且 `Theme_isLightTheme == false` → 关
8. 其它：`boolean forceDark = Theme_forceDarkAllowed`，缺省值 `!mIsDarkModeSupported` → 开/关

Theme 属性下标已核实：`Theme_forceDarkAllowed = 0x116 (278)`，`Theme_isLightTheme = 0x117 (279)`（`反编译\framework-selected\styleable.java`；`ForceDarkHelperStubImpl` smali 中为字面量 `0x116/0x117`）。`framework-res` 的 `Theme` 本身不设 `forceDarkAllowed`，只有 `values-night` 的 `Theme.DeviceDefault.SystemUI` 显式设为 `false`（`反编译\framework-res\res\values-night\styles.xml`）。

`mIsDarkModeSupported` 为原生方法 `AssetManager.nativeIsDarkModeSupported`。对 `libandroidfw.so` 做 Ghidra headless 反编译可见：`AssetManager2::IsDarkModeSupported()` 遍历各 `LoadedPackage`，命中 `LoadedPackage::IsDarkModeSupported()`；后者在资源表中检查 `drawable` 类型、配置字节满足 `(x & 0x30) == 0x20`（night 位）的条目，计数 **> 0x14（20）** 时返回 true。即：**这是「夜间 drawable 资源条目数 > 20」的启发式判定，不是应用声明的 API**（字段偏移的语义为反编译推断，见 §六）。

证据：`解包\ghidra-isDarkModeSupported.log`；`分区\system_a\system_a\system\lib64\libandroidfw.so`。

### 3.4 名单：`ForceDarkAppSettings.json` + 云

本地文件：`/system_ext/etc/forcedarkconfig/ForceDarkAppSettings.json`（展开后 `分区\system_ext_a\system_ext_a\etc\forcedarkconfig\`）。

- 共 **130** 条；字段：`packageName / showInSettings / defaultEnable / overrideEnableValue / forceDarkOrigin / forceDarkSplashScreen / adaptStat / interceptRelaunch`。

### 3.6 主题与「原生深色支持」

当应用既不是白名单也不是黑名单时：

```java
boolean forceDark = a.getBoolean(0x116 /*Theme_forceDarkAllowed*/, !mIsDarkModeSupported);
```

- 应用主题显式 `android:forceDarkAllowed="false"` → 不反色；显式 true → 反色。
- 未声明时，看 `mIsDarkModeSupported`：原生判定认为「有夜间资源」→ 不反色；否则反色。
- 应用代码里任何 View 调 `View.setForceDarkAllowed(false)` 也会局部关闭（`ViewForceDarkStateImpl.mForceDarkAllowed`）。

这解释了两类现象：自带深色主题的应用（不需要反色）开关打开后看不出变化；以及在某些页面由应用主动关闭反色的应用。

证据：`反编译\framework-selected\View.java`（`View_forceDarkAllowed` 属性解析、`setForceDarkAllowed`）；`反编译\miui-framework\sources\android\view\ViewForceDarkStateImpl.java`。

### 3.7 WebView 与逐 View

`drawBlackMask()`：若 `secondaryRule & 32 != 0` 且当前 View 是 `WebView` 且没有匹配到 View 配置，则：

```java
view.setForceDarkAllowed(false);
canvas.drawColor(Color.parseColor("#50000000"));
```

即 WebView **不做反色，只盖一层 50% 黑**。混合应用（主界面是 WebView）看起来就是「变暗了但没反色」或「完全没变」。另外 `SurfaceView`/视频层不经过 HWUI 反色，也不受该开关影响。

证据：`反编译\miui-framework\sources\android\view\ForceDarkHelperStubImpl.java`，`drawBlackMask` / `updateBackgroundDrawable` / `updateBeforeViewDraw`。

### 3.8 渲染层

真正的反色由原生库执行：
- `android.graphics.MiuiForceDarkConfigManagerImpl` 静态块 `System.loadLibrary("forcedarkimpl")`，`setConfig(density, main, secondary, tertiary)`。
- `libhwui.so` 内含 `ForceDarkConfigStub` / `forcedarkimpl` 符号；`system_ext/lib64/libforcedarkimpl.so` 内含 `ForceDarkConfigManagerImpl` / `ForceDarkConfig` / `usageHint` 等符号。
- Java 侧只负责「开/关 + 规则」，像素级转换在 HWUI/forcedarkimpl。

证据：`反编译\miui-framework\sources\android\graphics\MiuiForceDarkConfigManagerImpl.java`；`提取的APK\原生库\libforcedarkimpl.so`、`libhwui.so`。

### 3.9 全局深色与 AOSP 旁路（Android 16 新增）

- 全局深色关闭时，第 3 步直接关；per-app 开关只是被记录下来，不产生效果。
- `mForceDarkOrigin=true` 时 MIUI 返回 false，`ViewRootImpl` 回落到 AOSP `determineForceDarkType()`：
  - 普通路径：`night && Theme_isLightTheme && Theme_forceDarkAllowed`（缺省取系统属性 `debug.hwui.force_dark`，默认 false）。
  - Android 16 新增「强制反色」：若 aconfig `android.view.accessibility.force_invert_color` 开启、系统处于深色、且 `Settings.Secure accessibility_force_invert_color_enabled == 1`，则 `UiModeManager.getForceInvertState()==1`，对「浅色主题 + 浅背景」的窗口返回 type 2（强制反色）。
- 这条旁路完全不受「应用单独设置」控制，是全局的。若用户开过无障碍里的强制反色，origin 应用的观感会和 MIUI 开关不一致。

证据：`反编译\framework-selected\ViewRootImpl.java`（`determineForceDarkType` / `shouldApplyForceInvertDark`）；`反编译\framework-selected\UiModeManager.java`；`反编译\miui-services-full` 外的 AOSP `UiModeManagerService`（`分区\system_a\...\services.jar`，方法 `isForceInvert` 读 `accessibility_force_invert_color_enabled`）。

### 3.10 名单切换的重启策略（补充）

`ForceDarkHelperStubImpl.shouldInterceptUiModeRelaunch()` / `adaptUiModeConfigChanged()` 决定全局深色切换时应用是否被重启：`interceptRelaunch=1` 不重启、直接下发配置变化；=2 正常重启；=3 去除 `CONFIG_UI_MODE` 变化位。调用点在 `ActivityThread.performActivityConfigurationChanged`（framework）和 `ActivityRecordImpl`（miui-services）。
注意：这只影响**全局深色开关**，与 per-app 开关无关；per-app 开关不会给应用发任何 `Configuration`。

## 四、为什么「有时生效，有时不生效」

按现场概率排序。每条都给「触发条件 → 现象 → 证据」。

### 4.1 进程缓存 + 观察者注册时机（最常见）

- **条件**：开关切换时，目标应用进程还活着，但**尚未创建过任何窗口**（只有 Service/后台进程），或进程的 `mForceDarkOrigin` 为 true 导致从未注册观察者。
- **结果**：服务端的 `setAppDarkModeEnable` 找不到该 pid 的观察者，回调不到；进程内 `mIsAppDarkModeEnable` 保持启动时的旧值。之后即使打开界面（新 `ViewRootImpl` 注册观察者），也**不会补发当前值**，必须等下一次开关切换或杀进程。
- **用户观感**：同一应用，有时切完就有用，有时必须「强行停止」再开。
- 证据：§3.2 的注册条件与 `onAppDarkModeChanged`；`ViewRootImpl` 构造函数注册、`handleAppVisibility` 只做重算不做重读。

### 4.2 切换时应用不可见

- **条件**：应用在后台/被遮挡时切换开关。
- **结果**：`refreshForceDarkMode(false)` 只刷新 `mAppVisible` 的窗口，当时不生效；但若观察者已注册，回调已把新值写进缓存，**下次回到前台**（`handleAppVisibility`）会补上。
- **用户观感**：切完切回应用才生效，或以为没生效。若应用进程随后被 LMK 杀掉，重启后读 DB 反而正常。

### 4.3 名单内配置的静态差异（按 app，不是按次）

| 条件 | 结果 | 证据 |
|---|---|---|
| 包不在 130 条名单（中国版）→ `mForceDarkOrigin=true` | MIUI 完全不接管，开关无意义 | §3.4 |
| 有 `<pkg>.json` 且 `forceDark:false` | 黑名单，开关打开也无效 | §3.5 |
| 有 `<pkg>.json` 且 `forceDark:true` | 白名单，开关打开必生效（列表内 43 个） | §3.5 |
| 列表内但无配置文件（4 个） | 回落到主题/原生判定，可能不生效 | §3.6 |
| 应用自带夜间资源（启发式 >20 个 night drawable） | 未列名的应用默认不反色 | §3.3 |

### 4.4 同一应用内不同页面

- 命中了 `forceDarkActivityConfigList` 中 `forceDark:false` 的 Activity → 该页不反色；当前样本 29/363。
- 命中了 View 级 `forceDark:false` 或应用自己 `setForceDarkAllowed(false)` → 局部不反色。
- WebView → 不反色只盖黑罩；视频/SurfaceView → 不参与反色。
- 证据：§3.5、§3.7。

### 4.5 云配置/名单与进程启动的时序

- 本地名单在 `ForceDarkAppListProvider` 构造时同步读取；云名单/云配置在 boot phase 550 之后用 `CompletableFuture` **异步**拉取。
- 应用进程启动早于云配置落地 → 读到的是旧名单/旧配置；之后云配置更新不会推送到已运行的 app 进程：
  - 名单变化：`notifyAppListChanged()` 只通知 **SystemUI** 的 splash 映射，不通知应用进程。
  - 配置文件变化：`onForceDarkConfigChanged()` 由 `ForceDarkUiModeModeManager` 的监听器调用，而该管理器在 **system_server** 里，更新的是 system_server 自己的 `ForceDarkHelperStub` 实例，不是各 app 进程。
- 另外 `mForceDarkOrigin`、`mIsBlackAppDarkMode`、`mIsWhiteAppDarkMode` 在配置更新时都**不重算**（`onForceDarkConfigChanged` 只替换 `mForceDarkAppConfig`）。
- 用户观感：同一应用「上次开机有效、这次无效」「更新/重启一段时间后才对」。

### 4.6 依赖失败时的静默降级

- `getDarkModeAppSetting`（16777213）binder 失败 → 返回 **false**（开关视为关）。
- `getForceDarkOriginState`（16777209）binder 失败 → 返回 **true**（视为 origin，MIUI 不接管）。
- 两者都没有重试。任何一次瞬时失败都会让该进程整段生命周期不反色。
- 证据：`ForceDarkHelperStubImpl.getDarkModeAppSetting` / `getForceDarkOriginState`。

### 4.7 全局条件与特殊分支

- 系统深色模式关闭（`uiMode` 非 night）→ 所有应用都不反色，per-app 开关不产生效果。
- 输入法进程 → 永久跳过。
- 系统应用且 `isLightTheme=false` → 永久跳过。
- 无障碍「强制反色」开启时，origin 应用可能被 AOSP 旁路反色，与 MIUI 开关无关。

### 4.8 一个「算得出来」的结论

对列表内、有 `forceDark:true` 配置的应用，单次开关行为本应是确定的；出现「有时」几乎只能落到 **4.1/4.2/4.5/4.6** 这几条与进程状态相关的分支。对列表外/黑名单/无配置应用，则是 **4.3** 的静态规则在起作用——那不是「时灵时不灵」，是「本来就按配置不做」。

## 四·补充、超频工具（`com.flydigi.waspwing.experimental`）冷启动不稳定的归因

### 4.9.1 名单位置：本地没有，只能来自云端

ROM 静态文件里的事实：

- `ForceDarkAppSettings.json` 的 130 条中**没有** `com.flydigi.waspwing.experimental`（也没有 `com.flydigi.waspwing`、`com.flydigi.waspwing.experimentanliuliu`）。
- `system_ext/etc/forcedarkconfig/` 下**没有**这三个包的 `<pkg>.json`。
- ROM 各分区中未发现该包的同名目录、配置或清单条目（按目录名 / `*.xml` / `*.json` / `*.prop` 检索均为空），判断为用户侧安装的三方应用。

推论（基于 §3.4 的中国版列表逻辑）：设置页「应用单独设置」只列举 `mForceDarkAppSettings`（本地 + 云 `force_dark_app_settings_list`）中 `showInSettings=true` 的项。本地没有它，**而用户能在设置页给它拨开关，说明云名单 `force_dark_app_settings_list` 里存在该包（或其 Settings 缓存文件残留旧条目）**。

补充：Settings 侧还有一层缓存 —— `DarkModeAppCacheManager` 以服务端返回的 `createTime` 为版本号，服务端 `createTime` 未变时返回 null，Settings 直接用 `/data/user/0/com.android.settings/files/dark_mode_app_data.json`。因此设置页**可能显示已不在当前云名单里的包**；此时服务端 `getAppForceDarkOrigin` 仍按当前名单算，可能就是 origin=true（白）。这也是「设置页能开、但开关没效果」的一条独立路径。云数据不在 ROM 镜像里，必须从设备侧读取确认（命令见 §4.9.5）。

### 4.9.2 它可能走哪条路径

`getAppForceDarkOrigin` 先查 `mForceDarkAppSettings`（本地 + 云快照）：

| 云名单状态 | `forceDarkOrigin` | MIUI 是否接管 | 后续路径 | 典型观感 |
|---|---|---|---|---|
| 无此包（或只有 Settings 缓存残留） | true | 否 | `ViewRootImpl` 回落 AOSP `determineForceDarkType()` | 多数为白：AOSP 要求 `isLightTheme` 且 `Theme_forceDarkAllowed`，未显式声明时缺省 false；主题显式允许反色的应用仍可能被 AOSP 反色 |
| 有条目、`showInSettings=true`、未写 `forceDarkOrigin` 或写了 false | false | 是 | 继续看每应用配置/主题 | 取决于下一行 |
| 有条目但显式 `forceDarkOrigin=true` | true | 否 | 同第一行 | 基本白色 |

MIUI 接管后，`mForceDarkAppConfig` 的来源（云 `force_dark_app_config` → 本地 `<pkg>.json`）：

| 配置 | 判定 | 结果 |
|---|---|---|
| `forceDark:true` | 白名单（第 6 步） | 暗（与主题/原生支持无关） |
| `forceDark:false` | 黑名单（第 5 步） | 白（用户开关无法覆盖） |
| 无配置（本地确实没有；云若也无） | 第 7/8 步：`isLightTheme` / `Theme_forceDarkAllowed`（缺省 `!mIsDarkModeSupported`） | 由 APK 主题与 night 资源决定；**同一个 APK 是确定值** |

所以这个包在 ROM 静态层面**不属于本地白名单也不属于本地黑名单**；它最终是「云白名单」还是「主题/原生路径」，取决于设备上的云 `force_dark_app_config`。如果云里也没有它的配置，这条路径对同一份 APK 是稳定的——这反而说明：**两次冷启动一黑一白，问题不在主题/原生判定，而在更前面的 `origin` / `enable` / 配置是否被读到**。

### 4.9.3 真正可能随冷启动变化的输入（按可能性排序）

#### (1) 进程是否「真冷」——最可能

- `initialize()` 每进程只跑一次；`registerAppDarkModeObserver()` 只在 `ViewRootImpl` 构造（即第一次建窗）时调用。
- 若该包有常驻进程（蓝牙/外设类应用通常有 Service、开机自启或通知栏常驻），用户拨开关时进程可能还活着但**从未建过窗口** → 不注册观察者 → 收不到 `onAppDarkModeChanged` → 进程内 `mIsAppDarkModeEnable`/`mForceDarkOrigin` 保持启动时的旧值。
- 之后从图标「冷启动」若复用该进程，实际是**热启动**：仍是旧值 → 白。进程被 LMK/手动杀掉后再启，才是真正新进程 → 读 DB/云 → 暗。
- 这条同时解释「都是冷启动却不一样」：用户看到的是冷启动，进程未必是新的。
- 证据：§3.2 的注册条件与 `onAppDarkModeChanged`；`ForceDarkHelperStubImpl` 的 `initialize` 单次性。

#### (2) 云名单的异步加载与快照

- `ForceDarkAppListManager` 构造时 `mForceDarkAppSettings = provider.getForceDarkAppSettings()` 只含本地 130 条；云在 boot phase 550 之后用 `CompletableFuture` 异步加载，加载完成后通过 `onChange()` 换快照。
- 应用进程若在云加载完成之前启动，`getAppForceDarkOrigin` 看不到该包 → 返回 true（origin）→ 本进程整段生命周期 MIUI 不接管 → 白。之后再冷启动（云已就绪）→ origin=false → 可能暗。
- 云数据被回滚/服务器下发一份不含该包的合法列表时，快照也会整体丢掉该包（`updateCloudForceDarkAppList` 解析成功但列表不同 → `onChange`）。
- 还有一级回退：若快照里没有该包，`getAppForceDarkOrigin` 会再看 `mDarkModeAppData`（Settings 查询列表时建立的缓存）。`clearCache()` 只重置 `createTime`、**不清列表**，所以「曾经在设置页出现过」的包在云名单移除后仍可能被判为非 origin，直到下一次列表重建。这让结果与「是否/何时打开过设置页」相关。
- 证据：`ForceDarkAppListProvider.onBootPhase` / `updateCloudForceDarkAppList`；`ForceDarkAppListManager` 构造器、`getAppForceDarkOrigin`、`clearCache`。

#### (3) 云配置读取的无锁竞态（同一次开机内也能复现）

- `ForceDarkAppConfigProvider.updateLocalForceDarkAppConfig()` 的执行顺序是：
  1. `mCloudForceDarkAppConfig.clear()`
  2. 读云 `configVersion`
  3. 解析 JSON、逐条 `put`
- 而应用进程的 Binder 16777211 → `getForceDarkAppConfig(pkg)` 在 system_server 的 binder 线程上**无锁直接读**这个 HashMap（`getCloudAppConfig` 先 `containsKey` 再 `get`）。
- 两者并发时，应用可能恰好落在「已 clear、尚未 put」的窗口 → 云配置返回 null → 回落到本地（本地又没有）→ `mForceDarkAppConfig=null` → 黑白标志都不置位 → 走主题/原生路径 → 很可能是白。
- 触发频率：`registerDataObserver` 监听的是云数据总通知 URI（`content://com.android.settings.cloud.CloudSettings/cloud_all_data/notify`），**任何云数据的更新都会让两个 provider 重跑一次**，所以这个窗口不是只在开机出现。
- 证据：`ForceDarkAppConfigProvider.java` 的 `updateLocalForceDarkAppConfig` / `getForceDarkAppConfig`；`ForceDarkUiModeModeManager` 的 `initForceDarkAppConfig`。

#### (4) Binder 静默降级

- `getDarkModeAppSetting`（16777213）失败 → 返回 false → 第 4 步直接白。
- `getForceDarkOriginState`（16777209）失败 → 返回 true → 第 1 步直接跳过 MIUI → 白。
- 两次调用都没有超时/重试；`transact` 返回 false 或抛 RemoteException 时只打 `Slog.e(TAG, "...transact failed...")`，不影响返回值。
- 开机早期、system_server 高负载、服务尚未发布时更容易命中；之后进程重启即可恢复。
- 证据：`ForceDarkHelperStubImpl.getDarkModeAppSetting` / `getForceDarkOriginState`。

#### (5) 全局深色状态

- `mIsDarkModeEnabled` 来自进程启动时的 `Configuration.uiMode`。系统处于浅色（或自动深色正在切换的边界）时，per-app 开关一律不生效 → 白。
- 证据：`updateForceDarkMode` 第 3 步。

#### (6) `mIsDarkModeSupported`（基本排除为随机源）

- 它是原生方法对**当前 AssetManager 里的资源表**做扫描（night 配置位条目计数 >20），对同一份已安装 APK 是纯函数；只有 split APK / 动态资源 / overlay 的加载状态在进程初始化时不稳定时才可能变化。
- 因此它更可能解释「这个 app 从来都是白/从来都是暗」，而不是「同一 APK 一黑一白」。证据：§3.3 的 Ghidra 结果。

#### (7) 应用自身运行期关闭反色

- 应用可在代码里调用 `View.setForceDarkAllowed(false)`，或使用 WebView（MIUI 只盖黑罩）、SurfaceView/视频层（不参与 HWUI 反色）。
- **判定是按窗口（`ViewRootImpl`）做的，主题取自该窗口的 Context**。同一个应用若有多个主题（Splash/启动页、主页、弹窗 Activity），不同窗口可以拿到不同的 `Theme_forceDarkAllowed`/`isLightTheme`；冷启动时先出现的窗口（启动页 vs 直接恢复的 Activity）不同，观感就可能不同。这条需要 APK 的 manifest/theme 才能确认。
- 对外设/游戏类应用，若主界面含 WebView 或 GL/Surface 层，观感会是「没反色/只变暗」。这不是冷启动随机源，但会把「暗/白」的判断搅浑；需要拿到 APK 后按 §4.9.5-E 复查。

### 4.9.4 为什么两次冷启动会不同（归因结论）

- 若两次都是真正的**新进程**，且云数据已就绪，那么 `origin`、`enable`、`mIsDarkModeSupported`、主题属性都是确定值，理论上不该不同。
- 因此最可能的解释是以下三者的组合：
  1. **其中一次并不是真冷启动**（进程被常驻服务/自启动拉起，复用了旧的 `initialize()` 结果；见 (1)）；
  2. **其中一次启动落在云名单/云配置尚未就绪或正在刷新的窗口**（见 (2)(3)）；
  3. **其中一次 Binder 调用静默失败**（见 (4)）。
- 如果用户每次都 `am force-stop` 后启动、并且开机已久（云早已就绪），仍然一黑一白，则 (1)(2) 基本可以排除，应重点查 (3)(4)，并用下面的日志直接看 `reason`。

### 4.9.5 设备侧验证命令（需要用户执行）

> 该包不在 ROM 镜像里，云配置内容与该 APK 的 manifest/theme 都只能从设备取；以下命令均为只读。

**A. 先确认「冷启动」是不是真冷**

```bash
adb shell ps -A | grep -i waspwing
# 启动应用后再执行一次；PID 不变 = 不是冷启动，直接命中归因 (1)
adb shell dumpsys activity processes | grep -i -A30 waspwing
# 若要看进程启动时间：adb shell "cat /proc/<PID>/stat" 的第 22 字段（starttime，单位为开机后的 clock tick）
```

**B. 每次启动抓判定原因（关键，无需开 debug）**

```bash
adb logcat -c
# 打开超频工具，然后：
adb logcat -d -s ForceDarkHelperStubImpl | grep -E "setViewRootImplForceDark|transact failed"
```

- 看到 `reason: WhiteAppDarkMode` → 云配置确实有 `forceDark:true`，走白名单；
- `reason: DarkModeEnabled` → 当时系统不是深色（全局条件）；
- `reason: AppDarkModeEnable` → 服务端开关读到 false（Binder 失败或 DB 值不对）；
- `reason: BlackAppDarkMode` → 云配置是黑名单；
- `reason: forceDarkAllowed` → 走到了主题/原生兜底（云配置缺失或未读到）；
- 出现 `transact failed` → 直接命中归因 (4)。
- 两次启动的 `reason` 不同，就能把「不稳定输入」精确指到对应的一步。

**C. 读云名单与云配置原文（root；这是「设置页为什么有它」的唯一直接证据）**

云数据由 `com.android.htmlviewer`（HTMLViewer，进程 `:remote`，directBootAware）的 `CloudSettingsProvider` 提供，DB 文件是 `cloud_all_data.db`，表 `cloud_all_data`，列 `moduleName` / `productData`。数据库可能在 `/data/user/0/`，开机直读阶段也可能在 `/data/user_de/0/`，两条路径都试：

```bash
# 有 sqlite3 的设备：
adb shell su -c "sqlite3 /data/user/0/com.android.htmlviewer/databases/cloud_all_data.db \"select productData from cloud_all_data where moduleName='force_dark_app_settings_list'\""
adb shell su -c "sqlite3 /data/user/0/com.android.htmlviewer/databases/cloud_all_data.db \"select productData from cloud_all_data where moduleName='force_dark_app_config'\""

# 没有 sqlite3：
adb shell su -c "cp /data/user/0/com.android.htmlviewer/databases/cloud_all_data.db /sdcard/cloud_all_data.db"
adb pull /sdcard/cloud_all_data.db
# 本地 Python：
python -c "import sqlite3,json;c=sqlite3.connect('cloud_all_data.db');print([r[0] for r in c.execute(\"select productData from cloud_all_data where moduleName='force_dark_app_settings_list'\")])"
```

> 若 `/data/user/0/...` 不存在，把路径换成 `/data/user_de/0/com.android.htmlviewer/databases/cloud_all_data.db` 再试。
> Git Bash/Windows 下多层引号容易被改写：可先 `adb shell` 进交互再执行，或把 SQL 写入 `q.sql` 后 `adb push q.sql /data/local/tmp/`，再 `adb shell su -c "sqlite3 <db> < /data/local/tmp/q.sql"`。

在输出里搜 `com.flydigi.waspwing.experimental`，确认三件事：是否在 `force_dark_app_settings_list`、`showInSettings` 是否 true、是否写了 `forceDarkOrigin`；以及 `force_dark_app_config` 里是否有它的 `<pkg>.json` 等价条目、`forceDark` 是 true 还是 false。

**D. 确认开关真的写进去了**

```bash
adb shell settings get system last_app_dark_mode_pkg
# 期望：com.flydigi.waspwing.experimental:true
adb shell settings get secure ui_night_mode
adb shell settings get system dark_mode_enable
adb shell dumpsys uimode | head -40
```

**E. 取 APK 做静态核对（manifest / theme / 进程）**

```bash
adb shell pm path com.flydigi.waspwing.experimental
adb pull <上一步输出的 base.apk 路径>
adb shell dumpsys package com.flydigi.waspwing.experimental | grep -i -E "processName|android:process|force_dark|theme"
```

拿到 APK 后可以核对：manifest 是否声明 `force_dark_google`（有则永远 origin、与开关无关）；应用主题是否显式 `forceDarkAllowed`；是否多进程/常驻服务（验证归因 (1)）；night drawable 数量（验证原生判定）。

**F. A/B 对照（把 origin/enable 因素固定住）**

```bash
adb shell setprop sys.forcedark.debug 32   # 应用进程启动时读取：origin 强制 false、app enable 强制 true
adb shell am force-stop com.flydigi.waspwing.experimental
# 再启动，抓 reason；若此时稳定为暗/稳定为白，说明波动来自 origin/enable（(1)(2)(4)）；
# 若仍然一黑一白，问题在配置/主题/应用自身。
```

**G. 注意 `dumpsys uimode` 的前置条件**

`ForceDarkUiModeModeManager.mForceDarkDebug` 在 **system_server 启动时**读取 `sys.forcedark.debug`；开机后再 `setprop` 不会让 dump 生效（需要重启，或改用 B 的日志法）。因此不推荐把 `dumpsys uimode` 作为第一手段。

### 4.9.6 证据不足的部分

- 云 `force_dark_app_settings_list` / `force_dark_app_config` 的实际内容（决定 origin 与黑白名单）不在 ROM 镜像里，**必须按 §4.9.5-C 取设备数据**，否则无法断定该包是「云白名单」「云黑名单」还是「主题/原生兜底」。
- 该 APK 的 manifest（`force_dark_google`、多进程、常驻 Service）与主题属性（`forceDarkAllowed` / `isLightTheme`）同样不在镜像里，需按 §4.9.5-E 取 APK。
- 因此本节的结论是「把不稳定输入收敛到可验证的 4 个点」，而不是单点定论；`reason` 日志（B）能一次性判死。

## 五、可行的规避 / 修复方向

### 5.1 用户侧（不改系统）

1. 切换开关后，若应用已在后台常驻，直接「强行停止」再打开；不要只看几秒内的效果。
2. 确认系统深色模式本身处于开启状态（per-app 开关只在深色下有效）。
3. 对同一应用逐页验证：有些页面是配置里显式关闭的（视频、WebView、相机预览），不是故障。
4. 开关打开后进入应用的多任务/分屏再返回，触发一次 `handleAppVisibility` 重算。

### 5.2 诊断侧（只读，不改系统）

- `adb logcat -s ForceDarkHelperStubImpl` **无需开 debug** 即可看到每次判定的 `setViewRootImplForceDark: <bool> for <Activity>, reason: <reason>`（该 `Slog.i` 无条件打印，见 §3.3），`reason` 直接对应判定步骤（`DarkModeEnabled` / `AppDarkModeEnable` / `BlackAppDarkMode` / `WhiteAppDarkMode` / `LightTheme` / `forceDarkAllowed`）。`setprop sys.forcedark.debug 2` 只是额外打印初始化耗时等信息。
- `setprop sys.forcedark.debug 32` → `getForceDarkOriginState` 强制返回 false、`getDarkModeAppSetting` 强制返回 true，用于排除名单/开关因素。
- `setprop sys.forcedark.debug 16` → 允许从 `/data/data/<pkg>/<pkg>.json` 加载调试用 per-app 配置（`loadForceDarkConfig`）。
- `setprop sys.forcedark.debug 2` 后 `adb shell dumpsys uimode` 可 dump 每个已注册进程的 `mForceDarkOrigin / mIsAppDarkModeEnable / mIsBlackAppDarkMode / mIsWhiteAppDarkMode / mIsDarkModeSupported`。
- `adb shell settings get system dark_mode_enable`、`adb shell settings get secure ui_night_mode` 查看全局状态。

### 5.3 ROM / 模块侧（需要改系统，本次未执行）

1. **最小修复**：在 `ForceDarkHelperStubImpl.updateForceDarkMode()` 开头按需重读 `getDarkModeAppSetting`，或在 `registerAppDarkModeObserver` 成功后主动拉一次当前值（解决 4.1 的「注册不回填」）。
2. 让 `onForceDarkConfigChanged` 同时重算 `mIsBlackAppDarkMode / mIsWhiteAppDarkMode / mForceDarkOrigin`，并建立向 app 进程推送配置的通道（解决 4.5）。
3. 名单外应用若要强制深色：在 `/system_ext/etc/forcedarkconfig/ForceDarkAppSettings.json` 增加 `showInSettings:true` 条目，并补 `<pkg>.json` 且 `forceDark:true`（或其云模块同名条目）。
4. 对「某页面不反色」：在 `<pkg>.json` 的 `forceDarkActivityConfigList` 里把该 Activity 的 `forceDark` 置 true（默认继承应用配置，只有显式 false 才关）。
5. LSPosed 方案（不刷机）：hook `android.view.ForceDarkHelperStubImpl.updateForceDarkMode(ViewRootImpl)`，在返回前按当前 DB/用户设置重新计算并 `setViewRootImplForceDark(...)`；或 hook `initialize` 后在每次 `ViewRootImpl` 构造时重新调用。注意这是修改运行时行为，需用户自行承担风险。

## 六、未验证项与风险

1. **`AssetManager.isDarkModeSupported` 的精确谓词**：Ghidra 反编译显示其按资源表 `drawable` 类型、night 配置位计数，阈值 20；但 `ResTable_config` 字段偏移的语义是推断（函数被大量 STL/locale 采集代码内联，类型传播未完全收敛）。对**列表内 43 个白名单应用无影响**（白名单短路），只影响 4 个无配置应用和名单外应用。
2. **云配置内容不可见**：`force_dark_app_settings_list` / `force_dark_app_config` 来自 `MiuiSettings.SettingsCloudData`，ROM 里没有实际云数据。用户机上云项可能改变 `showInSettings`、`forceDarkOrigin`、`forceDark`，从而改变「哪些应用能出现在列表、开关是否有效」。本报告对静态名单的统计仅基于本地文件。
3. **AOSP `force_invert_color` aconfig 默认值**：`android.view.accessibility.Flags.forceInvertColor()` 的默认值在设备 aconfig 缓存里，ROM 镜像中无法直接读出；无法确认该旁路在用户机上是否默认开启。
4. **`interceptRelaunch` 的实际效果**：调用点已确认（`ActivityThread.performActivityConfigurationChanged`、`ActivityRecordImpl`），但本次未做动态验证；它只影响全局深色切换的重启策略。
5. **具体是哪个应用**：报告给的是机制和静态名单统计。§四·补充已对 `com.flydigi.waspwing.experimental` 做专项归因，并给出收敛到 4 个可验证输入的设备命令；最终单点定论仍需现场 `logcat` 的 `reason` 字段、云 DB 内容与该 APK 的 manifest/theme（§4.9.5）。
6. **反编译产物可靠性**：`baksmali` 对超大 dex 类（如 `ViewRootImpl`）输出不完整（本次已改用 jadx 交叉验证）；jadx 对混淆常量会把字面量改写成同名枚举（如 `NR5G_BAND_258`），本报告已回到 smali 字面量核对为 `0x116/0x117`。
7. 本次为**只读分析**：未在真机上验证任何 hook/修改；§5.3 的方案未执行、未验证。
