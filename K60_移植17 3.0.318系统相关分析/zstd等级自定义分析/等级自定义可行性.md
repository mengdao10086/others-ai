# K60 上自定义 zram zstd 压缩等级 —— 可行性分析

基于 `boot_Nemo.img` md5 `f125f9948087c7bc0fe3e21e91000935`（kernel md5 `3e52a6eb6e3b57d5ae48378483474d1e`，38,623,744 B）。

- 分析日期：2026-11-15
- 目标内核：`D:\下载\Mi\备份\k60\K60_移植17 3.0.318[68F32]\images\boot_Nemo.img`
- 方式：只读分析（raw Image 字符串/符号/反汇编 + IKCONFIG + 公开源码）；未刷机、未写系统分区、未改任何原始镜像
- 与上一份报告的关系：上一份的 zram 后端、`comp_algorithm` 无白名单、源码仓库等事实仍然成立；但「压缩等级固定为 3、需另写模块」这一条**被本报告推翻**（原因见 §2）。

---

## 一、一句话结论

**可行且代价可接受（近乎零成本）**：boot_Nemo 的 `5.10.257-android12-9-Kirara-26Y08Alkane-nemo` 内核**已经自带可写的 sysfs 模块参数** `/sys/module/zstd/parameters/compression_level`（默认 `1`，有效 `1–22`，权限 `0644`）。root 写入后，在 zram 压缩上下文创建/重建时生效即可；**不需要另写 crypto 模块，也不需要重编内核**。

前置条件：

1. 设备实际运行的是 **boot_Nemo**（官方 `boot_official.img` 没有这个参数，zstd 仍是固定等级）。
2. 有 root。
3. 在 zram 的压缩上下文创建前写入参数，或写入后 reset/重建 zram（原因见 §5）。

---

## 二、现状：等级是多少、用户态碰不碰得到

### 2.1 直接回答

- **boot_Nemo 上不是固定 level 3**：默认值是 `1`，且用户态可以直接改。
- **可写节点**：`/sys/module/zstd/parameters/compression_level`（root，0644）。
- 上一份报告判「固定 3」，是因为它依据的是公开仓库 `5.10.245` 的 `crypto/zstd.c`（`#define ZSTD_DEF_LEVEL 3`、无 `module_param`）。实际 boot_Nemo 是 `5.10.257`，带有**未推送的本地补丁**，把等级改成了可调全局变量。

### 2.2 二进制证据（boot_Nemo `kernel`）

从 raw Image 的 kallsyms（`CONFIG_KALLSYMS_ALL=y`）还原出以下符号：

| 符号 | 地址 | 含义 |
|---|---|---|
| `compression_level` | `0xffffffc00a2dcba0` | 等级全局变量，`.data` 初始值 = **1** |
| `__param_str_compression_level` | `0xffffffc009de3bd8` | 参数字符串 `"zstd.compression_level"` |
| `__param_ops_compression_level` | `0xffffffc009de3bf0` | `{set=set_compression_level, get=param_get_int}` |
| `__param_compression_level` | `0xffffffc00a064bd8` | `struct kernel_param` |
| `set_compression_level` | `0xffffffc008859010` | 写入回调 |
| `zstd_compress` | `0xffffffc008858cf8` | 每次压缩读取 `compression_level` |
| `__zstd_init` | `0xffffffc0088587f4` | 建 ctx 时读取 `compression_level` 并按它分配 workspace |

`struct kernel_param`（file offset `0x2064bd8`）逐字段解码：

- `+0x00 name` → `"zstd.compression_level"`
- `+0x08 mod` → `NULL`（内建）
- `+0x10 ops` → `{flags=0, set=set_compression_level.cfi_jt, get=param_get_int, free=NULL}`
- `+0x18 perm` → `0x01a4` = `0644`（root 可写）
- `+0x20 arg` → `0xffffffc00a2dcba0`（即 `compression_level`）

`zstd_compress` 反汇编（`0xffffffc008858d18` 起）：

```
ldr  w8, [x8, #0xba0]      ; 读 compression_level
cbz  w8, use_default       ; 0 -> 3
tbnz w8, #0x1f, use_zero   ; 负数 -> 0（ZSTD 视为默认）
cmp  w8, #0x16             ; >22 -> 22
...
```

`set_compression_level`（`0xffffffc008859010`）：`sscanf("%i")` 后夹取；实测控制流为：`0 -> 1`、`1..22` 原样、`>22 -> 22`、负数落到默认。

**sysfs 路径推导**（`kernel/params.c`，公开仓库同版本）：`param_sysfs_builtin()` 按 `kernel_param->name` 的第一个 `.` 拆成模块名与参数名，`kernel_add_sysfs_param(mk, kp, kp->name + name_skip)` 用去掉前缀后的名字建属性。因此：

```
/sys/module/zstd/parameters/compression_level
```

（不是 `.../zstd.compression_level`；`zstd.` 只是内建模块的前缀，见 `include/linux/moduleparam.h` 的 `MODULE_PARAM_PREFIX KBUILD_MODNAME "."`。）

### 2.3 对照组：官方内核没有这个参数

`boot_official.img`（md5 `c46e69b0e35bcfaf23e13878ddcfb55e`，`Linux 5.10.236-android12-9-...`）：

- Image 中搜不到 `zstd.compression_level`；
- 符号表里没有 `compression_level` / `set_compression_level`；
- `zstd_compress` 直接读 `.rodata` 的固定参数表，不读全局。

即：**可调等级是 boot_Nemo 独有的补丁**，官方内核仍是固定等级。

### 2.4 zram 侧：没有等级节点，但接受任意已注册算法

- 本机 `zram.ko`（5.10.160-gki）只有 `comp_algorithm`、`low_compress_ratio`、`num_devices`；**没有 `comp_params`**（那是 5.16+ 才有的接口）。
- `comp_algorithm_store` 反汇编：`strlcpy` → `strlen` → `crypto_has_alg(name, 2, 0xf)` → `strcpy`，**无白名单**。
- `zcomp_create` 反汇编：`crypto_has_alg(name, 2, 0xf)`，不通过返回 `-EINVAL`，**同样无白名单**。
- 因此 zram 接受 `zstd`（以及任何注册为 comp 类型的算法名）；等级不在 zram 侧传。
- 接口层面：v5.10 的 `crypto_comp_compress()`（zram.ko 实际引用的符号，见 `llvm-objdump -dr` 重定位）和 `scomp_alg.compress` 回调都**没有 level 参数**；等级只能来自 crypto 模块内部（上游是 `ZSTD_DEF_LEVEL 3`，boot_Nemo 是全局 `compression_level`）。

## 三、路径逐条评估

| 路径 | 可行性 | 卡在哪 | 工作量 | 风险 |
|---|---|---|---|---|
| **E（本报告新发现）直接用现有 sysfs 参数** | **可行** | 无（只要运行 boot_Nemo） | 几分钟（写节点 + 重建 zram） | 低（改错 level 只影响压缩率/失败，可改回） |
| A 另编 5.10 crypto 模块（`zstd-cl`） | 技术上可行，但**已无必要** | CFI/LTO 匹配、构建环境、struct 布局、模块 CRC | 约 200–400 行 + Linux 构建环境 + 真机测试 | 中高（加载失败/压缩异常） |
| B 重编整个内核，把 level 做成参数 | 技术上可行，但**已无必要** | 精确 `5.10.257` 源码未公开；LTO+PGO+BOLT+CFI 全量构建 + 刷 boot | 很高（需 Linux 构建机、完整工具链、刷机兜底） | 高（掉模块/不开机） |
| C 换可调后端 / `comp_params` 传 level | **不可行** | 5.10 zram 无 `comp_params`；`lz4`/`lzo`/`lzo-rle` 没有 level 参数 | — | — |
| D 用户态/脚本层（不碰内核） | **可行 —— 就是 E** | 无 | 同上 | 低 |

说明：

- **A**：本报告顺手验证了「没有 `Module.symvers` 就拿不到 CRC」这个卡点**可以绕过**——`CONFIG_MODVERSIONS=y` 会把 `__kcrctab` 编进 Image，直接从 Image 提取即可（见 §4）。但既然内核已经有现成参数，A 的价值只剩「想验证自己写模块」。
- **B**：即便有源码，改 `crypto/zstd.c` 后重编也要面对该内核的 `CONFIG_LTO_CLANG_FULL`、`CONFIG_CFI_CLANG`、PGO/BOLT/MLGO 构建链，以及刷 boot 的不开机风险；收益与 E 完全相同。
- **C**：`comp_params` 在 5.10 zram 不存在（字符串表只有 `comp_algorithm`、`low_compress_ratio`、`num_devices`）；`CONFIG_CRYPTO_LZ4HC` 也没开。
- **D**：不需要任何内核改动；唯一前提是内核里已经有这个 sysfs 节点（boot_Nemo 有）。

## 四、源码可得性（A/B 的生死线）

### 4.1 公开源码的边界

- 仓库：`https://github.com/NetizenNemo/android_gki_kernel_5.10_common`
- 分支：`android12-5.10`（只有这一个分支）；最后一次 push `2025-11-23`；`Makefile` 里 `SUBLEVEL = 245`。
- 无 tag、无 GitHub Release、无 `Module.symvers` 或构建产物。
- 另一个仓库 `NetizenNemo/NemoKernelRelease` 只是一个刷机 App（NINC），`releases` 为空。
- 运行内核是 `5.10.257`、编译于 `2026-08-06` → **精确源码不在公开仓库里**（公开仓库落后 12 个 sublevel、约 9 个月）。
- `crypto/zstd.c` 的公开版本（`5.10.245` 仓库 / 上游 `v5.10.257`）都是 `#define ZSTD_DEF_LEVEL 3`、**0 个 `module_param`**。所以 `compression_level` 是作者本地未公开的补丁。

### 4.2 `Module.symvers` 卡点：可以绕过（已实测）

- `CONFIG_MODVERSIONS=y`（config 第 811 行）会把每个导出符号的 CRC 写进内核 Image 的 `__kcrctab`。
- 本报告的脚本从 raw Image 里定位 `__ksymtab`（12 B/项的 `SORT(___ksymtab+*)` 数组）与 `__kcrctab`（4 B/项的 `SORT(___kcrctab+*)` 数组），按同名索引配对，重建出「符号 → CRC」表。
- 校验：用 `boot_official` + ROM 自带 `zram.ko` 的 `__versions` 逐符号比对，**130/130 命中、0 不一致**（其余 10 个是 `zs_*`，属 `zsmalloc.ko`，本就不在内核里）——证明提取方法正确。
- 对 boot_Nemo 提取到的关键 CRC：

| 符号 | CRC |
|---|---|
| `module_layout` | `0x57390c3f` |
| `crypto_register_alg` | `0x69d058e9` |
| `crypto_unregister_alg` | `0x5a9b4efe` |
| `crypto_register_scomp` | `0xd038d524` |
| `crypto_unregister_scomp` | `0x5429e3a4` |
| `zstd_init_cctx` | `0x477f25a4` |
| `zstd_compress_cctx` | `0xc752ed9d` |
| `zstd_cctx_workspace_bound` | `0xbe6a8c96` |
| `zstd_get_params` | `0x6315c42c` |
| `zstd_is_error` | `0xafc6c68e` |
| `zstd_init_dctx` | `0x3ae34aeb` |
| `zstd_decompress_dctx` | `0xca1648d4` |
| `vzalloc` | `0x40a9b349` |
| `vfree` | `0x999e8297` |

- 另外，`kernel/module.c` 的 `check_version()` 只在「模块列了该符号、但 CRC 不同」时失败；模块**没列**的符号只打 `no symbol version` 警告并放行。所以一个手写的 `Module.symvers` 只要有至少一条正确项（让 `__versions` 非空），其余缺失不会阻止加载。
- **结论**：A 的「没符号表拿不到 CRC」不是死路；但 A 对用户目标已无必要。

### 4.3 附带发现（影响「实际跑的是哪个内核」的判断）

- boot_Nemo 的导出符号 CRC 与 ROM `vendor_dlkm` 里的 stock 模块**不一致**：`module_layout` 是 `0x57390c3f`，而 stock 模块（zram/zsmalloc/lzo/qca_cld3）是 `0x7c24b32d`；`zram.ko` 的 140 个导入符号里 **54 个 CRC 不同**。
- 顺带修正前一份报告：`0x2db3247c` 是把 `llvm-readelf` 十六进制文本当成了数值；stock 模块的真实 `module_layout` CRC 是 **`0x7c24b32d`**（官方内核也是这个值）。
- boot_Nemo Image 里**没有**标准的 `"disagrees about version of symbol %s"` 报错串（官方内核有），暗示该内核放宽/移除了 CRC 不一致的拒绝逻辑；这与 ROM 会把 boot_Nemo 和 stock 模块一起发相符。
- **含义**：如果用户现在确实在跑 boot_Nemo 且 zram 正常，说明该校验确已放宽；如果 zram 加载失败，则实际跑的是 `boot_official`，本报告推荐的 sysfs 参数就不存在。是否放宽**未逐指令确认**（见 §6）。

## 五、推荐路径与前置条件

### 5.1 运行态设置（会重建 zram，swap 内容会丢，先 `swapoff`）

```sh
su

# 1) 看当前状态
cat /sys/module/zstd/parameters/compression_level    # 默认 1
cat /sys/block/zram0/comp_algorithm                  # 看是否已经是 zstd
cat /sys/block/zram0/disksize                        # 记下原大小，重建时用

# 2) 拆掉旧 zram 并重建
swapoff /dev/block/zram0
echo 1 > /sys/block/zram0/reset
echo zstd > /sys/block/zram0/comp_algorithm
echo 9 > /sys/module/zstd/parameters/compression_level   # 目标等级：1–22

# 3) 按原大小重建（K60 规则：>2GB 取 50%，上限 4096MB；示例 4096M）
echo 4096M > /sys/block/zram0/disksize
mkswap /dev/block/zram0
swapon /dev/block/zram0 -p 32758
```

**为什么必须先设 level 再建 zram**：`__zstd_init`（`0xffffffc0088587f4`）在创建压缩上下文时按当时的 `compression_level` 计算并分配 workspace；`zstd_compress` 每次压缩虽然会重新读 level，但 workspace 不会放大。如果在旧 ctx 上直接把 level 调高，ZSTD 可能因 workspace 不足返回错误，zram 侧表现为 `Compression failed! err=...`。先设参数、再 `reset` + 重建，最稳。

### 5.2 开机持久化

Magisk / KernelSU 的 `post-fs-data.sh`（在 `sys.boot_completed=1` 的 post_boot 之前跑；zram.ko 已加载、disksize 还没设时最稳）：

```sh
#!/system/bin/sh
echo zstd > /sys/block/zram0/comp_algorithm
echo 9 > /sys/module/zstd/parameters/compression_level
```

- 如果脚本实际跑在 post_boot 的 `disksize` 之后：`comp_algorithm` 写入会被拒绝（`Can't change algorithm for initialized device`），此时需要在脚本里 `swapoff` + `reset` + 重建 zram，或把参数放到内核 cmdline。
- 内核 cmdline 写法：`zstd.compression_level=9`（内建模块参数按 `<mod>.<param>` 解析；需要重打包 boot）。

### 5.3 取值

- 有效 `1–22`；默认 `1`；`0` 会被设成 `1`；`>22` 截断为 `22`；负数落到 ZSTD 默认（3）。
- 建议显式写 `1–22` 中的值；`3` 是上游 `ZSTD_DEF_LEVEL` 的默认。

### 5.4 前置确认

```sh
uname -r   # 应为 5.10.257-android12-9-Kirara-26Y08Alkane-nemo
ls /sys/module/zstd/parameters/
```

如果 `parameters/` 下没有 `compression_level`，说明当前是官方内核（或别的内核），本报告的路径不适用。

### 5.5 等效替代（只给一句）

若目标是「更省内存」而非「调等级的折腾本身」：等级提升对 4KB zram 页的实际收益需真机实测，更直接的杠杆是 zram `disksize` / swappiness / 回写策略（用户已有 swap-controller、Zram 回写增强），以及 `comp_algorithm` 在 `lzo`/`lz4`/`zstd` 之间的取舍。

## 六、未验证项

1. **真机节点存在性与当前值**：本报告是离线分析，未连设备；`/sys/module/zstd/parameters/compression_level` 的路径是按 `param_sysfs_builtin` 逻辑推导的，未在真机 `ls`/`cat`。缺：`ls -l /sys/module/zstd/parameters/`、`cat .../compression_level`。
2. **真机 zram 现状**：当前 `comp_algorithm`、`disksize`、是否已 `swapon`、`zram.ko` 是否加载成功。缺：`cat /proc/swaps`、`cat /proc/modules | grep zram`。
3. **level 提升的实际收益**：`3`/`6`/`9` 对 4KB zram 页的压缩率与压缩延迟，未在本机实测。需要真机 A/B（同一批数据、`/sys/block/zram0/mm_stat` 的 `orig_data_size`/`compr_data_size`、压缩耗时）。
   - 同项未验证：调高 level 但未重建 zram 时，ZSTD 是否一定因 workspace 不足返回错误而非越界——依据 zstd 库的 workspace 检查（`ZSTD_resetCCtx_internal`），未逐指令验证；按 §5「先设 level 再建/重置 zram」可规避。
4. **Nemo 内核是否放宽 module CRC 校验**：证据是标准报错串缺失 + CRC 不一致；未逐指令确认 `check_version`/`resolve_symbol` 的补丁语义。缺：真机 `dmesg | grep -i version`、`insmod` 一个 CRC 不匹配的测试模块。
5. **官方内核的 zstd 是否确为 3**：二进制显示读固定参数表、无 `compression_level` 符号；未逐指令核对常量。
6. **`compression_level` 默认值 1**：从 `.data` 初始值读出（ELF program header 映射，file offset `0x22dcd60`）；未真机 `cat` 验证。
