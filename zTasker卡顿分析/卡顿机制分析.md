# zTasker 轻任务导致全系统卡顿的机制分析

- 分析日期：2026-11-11
- 分析对象：zTasker 2.3.14 解包二进制 + 本机 2.3.12 运行实例
- 前置报告：[分析报告.md](分析报告.md)（已排除「重启localsend 死循环」这一用户已知并已修复的问题；本报告不再重复解包与死循环分析）
- 本报告回答：**为什么执行一个很轻的任务（提醒、音量、开程序、热键触发）时，整个 Windows 会卡一下**

---

## 0. 结论速览

按「与轻任务共性 + 证据强度 + 影响面」排序：

| 排名 | 机制 | 证据强度 | 影响面 | 触发范围 |
|---|---|---|---|---|
| 1 | **任务调度器跑在主 UI 线程，而同一线程持有全局低级键鼠钩子**；执行期间任何阻塞都会让钩子线程停止抽消息，Windows 延迟/丢弃全系统键鼠事件 | 强（静态调用链 + 线程 Suspension A/B 运行时实证，见 §11） | 全系统输入 | 计划任务；以及主线程被占住时的热键事件 |
| 2 | **主题/鼠标速度/屏保类动作触发全系统 `WM_SETTINGCHANGE` 广播**；主题动作用 `SendMessageTimeout(HWND_BROADCAST, …, fuFlags=0, 1000ms)`，每个无响应窗口各等 1s | 强（反编译 + 动态复现 6.1s/次） | 全系统窗口/桌面 | 主题、鼠标速度、屏保、部分系统设置动作 |
| 3 | **提醒/提示/Toast 窗口的前台抢占与合成器/托盘操作**：`SetForegroundWindow`、`FlashWindowEx`、透明分层窗口、30ms `SetWindowPos` 滑入动画、`Shell_NotifyIcon(NIF_INFO)` | 中（反编译确认调用，未逐项计时） | 桌面合成器、任务栏、焦点 | 提醒、热键提示、Toast、开程序提示 |
| 4 | **运行程序类动作的进程创建**：`CreateProcess`/`ShellExecuteEx`（管理员用 `runas`），首启可能触发 Defender 实时扫描 | 中（代码确认，Defender 未动态归因） | 全系统 CPU/磁盘 | 运行程序、打开文件/URL |
| 5 | **音量动作每次都重新走 COM + 音频端点全量枚举**（`CoInitialize` + `MMDeviceEnumerator` + `EnumAudioEndpoints` + `CoUninitialize`） | 中强（反编译 + 本机实测 3–5ms/次，首次 19ms） | 音频服务/音频设备 | 音量加减/设置/静音/读取 |
| 6 | **重型系统动作**：分辨率切换、关机、锁屏、内存清理（`EmptyAllWrokSet` 清空所有进程工作集）、自删除（REALTIME/TIME_CRITICAL） | 强（反编译确认） | 全系统 | 仅对应动作 |
| 7 | **每秒条件检查**：4 个 1 秒进程监测在主线程上做全量进程枚举（1MB `NtQuerySystemInformation` + Toolhelp） | 强（反编译 + 本机实测 4.5/7.7ms） | 全系统输入/CPU 的周期性抖动 | 常驻，无任务也发生 |
| 8 | 每次执行全量保存 `Tasks.dat`（212KB）并写日志 | 中（日志实测 `Save结束，耗时0ms`） | 磁盘/杀软 | 所有任务，但通常很轻 |

**一句话主因：**zTasker 把「计划任务调度」和「全局低级键鼠钩子」放在同一条主线程上；计划任务执行时这条线程在同步等待（延时、等窗口、COM、广播、创建进程、显示 UI），期间无法处理 `WH_KEYBOARD_LL`/`WH_MOUSE_LL` 回调，Windows 于是把**全系统**的键鼠事件挂起，超过约 300ms 还会丢事件/摘钩子——所以哪怕任务本身很轻，执行瞬间整个桌面都会“卡一下”。（热键触发的任务本身跑在 HotKey 分发线程，但钩子回调仍依赖主线程；主线程被计划任务占住时，热键输入同样会被延迟。）

## 1. 主因证据链：调度器与全局钩子同线程

### 1.1 全局低级钩子装在主 UI 线程

`HotKey.dll` 的 `CHotKey::Start`（0x10001210）调用 `FUN_100037f0`，其中：

```c
DAT_1000b498 = SetWindowsHookExW(0xd, FUN_100057d0, DAT_1000b490, 0); // WH_KEYBOARD_LL，无条件
if (mouse_enabled)
    DAT_1000b494 = SetWindowsHookExW(0xe, FUN_10005620, DAT_1000b490, 0); // WH_MOUSE_LL
...
CreateThread(..., FUN_100034e0, ...);  // 回调分发线程（GetMessage 0x804/0x795）
```

- 键盘钩子是**无条件安装**的；鼠标钩子按「高级选项→禁用鼠标热键」开关决定。
- `SetWindowsHookExW(..., dwThreadId=0)` 的回调由**安装钩子的线程**负责抽消息时执行；安装发生在 `Start` 的调用线程。
- `Start` 在 zTasker 中的调用链：`CTaskListUI::InitWindow`（0x6e015d，日志字符串 `Add Task to UI Begin/End`）→ `FUN_006c67fa` → `CHotKey::Start`。这是 UI 初始化代码，运行在主线程。
- `FUN_100034e0` 只是**热键命中后的回调分发线程**（收到 0x804/0x795 后执行用户回调）；它不改变「钩子回调本身跑在安装线程」这一事实。
- **运行时已证实（§11）**：主窗口 `UIMainFrame` 在 PID 13028 的线程 **16184**；`_zTaskerHotkeyWindow_` 在另一线程 **10552**。挂起 16184 → 全系统收键延迟约 650ms；挂起 10552 → 无影响。钩子确实在 16184（主 UI 线程）上。

### 1.2 调度器也跑在同一主 UI 线程

`CTaskListUI::StartTaskTimer`（0x6e585c）在**主窗口**上装了两个 `WM_TIMER`：

```c
SetTimer(hwnd, 1, 1000, TaskTimerProc);   // 1 秒
SetTimer(hwnd, 2, 10000, TaskTimerProc);  // 10 秒（跨天/备份清理）
```

`TaskTimerProc`（0x6e59d7）在 `wParam==1` 时调用 `FUN_006bd7ce`。`FUN_006bd7ce` 是完整的任务条件求值器：按任务类型读取 `chkCpuProc`、`chkProcChk*`、`cmbNetSpd*`、`chkMem*`、`chkWin*` 等配置，并调用 `ProcessExistsByName` 做进程监测。

命中条件后的执行链：

```text
FUN_006bd7ce (1s WM_TIMER，主线程)
  → FUN_006c9310(task)
      → FUN_006c9b69(task, ...)
          → (**(code **)(*task + 0x34))()   // 任务对象的虚函数：执行动作
```

在上述函数体内**没有** `CreateThread`/`_beginthreadex`；也就是说动作默认在 `WM_TIMER` 所在的主线程上同步执行。动作里的「延迟」「等待窗口」「等进程」「COM 枚举」「广播」「显示窗口」都会把这条线程占住。

### 1.3 动态验证：钩子线程一忙，全系统键鼠就被延迟/丢弃

`机制验证/hook_stall_probe.cs` 在自己的线程上装 `WH_KEYBOARD_LL`，然后人为让该线程睡眠 N ms，再用 `keybd_event` 注入无害的 `VK_F24`，测量「注入 → 钩子回调」的延迟：

| 钩子线程阻塞时长 | 实测回调延迟 |
|---:|---:|
| 0（空闲） | 15–16 ms（测量基线） |
| 200 ms | 93 ms |
| 250 ms | 171 ms |
| 300 ms | 200 ms |
| 350 ms | 247 ms |
| 400 ms | **回调未到达（>3.5s 超时）** |
| 500 ms | **回调未到达（>3.5s 超时）** |

结论：

- 钩子回调延迟约等于「阻塞的剩余时长」；这就是任务执行瞬间全系统输入“卡一下”的直接来源。
- 阻塞超过约 300–400ms 后，Windows 不再等待该钩子（`LowLevelHooksTimeout` 默认约 300ms），事件被丢弃，钩子可能被系统静默摘除——表现为热键突然失灵、按键丢失。
- 这个实验只注入 F24、只阻塞一次，属于最小化验证；不影响 zTasker 进程。

### 1.4 为什么「开程序、提醒、音量、热键」都会中招

- **提醒/Toast**：在主线程 `ShowWindow` + `SetForegroundWindow` + `FlashWindowEx` + 透明分层窗口 + 30ms `SetWindowPos` 滑入动画 + 播放声音，通常几十到几百毫秒。
- **音量**：主线程同步走 COM/音频端点枚举，本机 3–19ms；设备多/蓝牙/HDMI 环境会更久。
- **开程序**：主线程 `CreateProcess`/`ShellExecuteEx`，首启 + Defender 扫描可达数百毫秒。
- **热键触发**：热键回调本身在 HotKey 分发线程执行，但**钩子回调仍依赖主线程**；只要主线程正被上一个计划任务占住，热键事件本身就会被延迟。
- **延迟/等待窗口**：复合任务里的「延迟 1000ms」「等待窗口 5s」直接让主线程睡/等，影响最大。

## 2. 机制 B：全系统 `WM_SETTINGCHANGE` 广播（主题/鼠标/屏保）

### 2.1 代码证据

`Utility.dll` 的 `Util::System::SetDarkMode`（0x10076ce0）在写完注册表后：

```c
SendMessageTimeoutW((HWND)0xffff, 0x1a, 0, 0x100a0f8c, 0, 1000, 0); // HWND_BROADCAST, WM_SETTINGCHANGE
SendMessageTimeoutW((HWND)0xffff, 0x1a, 0, 0x100a0fb0, 0, 1000, 0);
```

关键参数：`fuFlags = 0`（**没有** `SMTO_ABORTIFHUNG`），`uTimeout = 1000`。文档明确：广播消息时**每个窗口都可以用完整个超时**。桌面上只要有几个无响应窗口，单次调用就会累加到数秒。

同类动作：

- `Util::Hardware::SetMousePointerSpeed`（0x10031820）：`SystemParametersInfoW(SPI_SETMOUSESPEED, ..., fWinIni=3)`，`SPIF_UPDATEINIFILE|SPIF_SENDCHANGE`，内部同样广播。
- `Util::System::EnableScreenSaver`（0x10076630）：`SystemParametersInfoW(SPI_SETSCREENSAVEACTIVE, ..., 3)`，同样广播。

### 2.2 动态复现（本机）

用与 zTasker 完全相同的调用形状广播 `WM_SETTINGCHANGE`（`机制验证/broadcast_test.cs`）：

| 调用方式 | 单次耗时 | 返回 |
|---|---:|---|
| `fuFlags=SMTO_ABORTIFHUNG\|SMTO_BLOCK` | 96–250 ms | 成功 |
| `fuFlags=0`，lParam=NULL（zTasker 同款） | **6124–6415 ms** | 首次成功，后续 `ERROR_TIMEOUT(1460)` |
| `fuFlags=0`，不运行探针窗口 | **6124–6129 ms** | 同上 |

同期用 `window_resp.exe` 枚举本机 412 个顶层窗口：**12 个窗口在 300ms 内连 `WM_NULL` 都不回**，其中：

- `SystemSettings.exe`（Windows 设置，PID 32808）：`PersonalizationThemeChangeListener`、`WorkerW`、`Windows.UI.Core.CoreWindow`
- `wps.exe` / `wpscloudsvr.exe`（WPS，PID 11736/24376）：`QEventDispatcherWin32_Internal_Widget*`

这些窗口就是 6 秒的来源：广播按窗口逐个等 1s。**切主题任务执行时，zTasker 主线程会被这条广播阻塞约 6 秒**，同时全桌面所有顶层窗口都被迫处理 `WM_SETTINGCHANGE`。

鼠标速度/屏保的 `SystemParametersInfo(...SENDCHANGE)` 实测（`机制验证/spi_test.cs`，设置为当前值，不改变实际速度）：

| 调用 | 耗时 |
|---|---:|
| `SPI_SETMOUSESPEED` + `SPIF_SENDCHANGE` | 705–719 ms/次 |

### 2.3 影响面

- 主题、鼠标速度、屏保、部分系统设置动作：**整机 UI 冻结 0.7–6 秒**，且所有顶层窗口被广播。
- 不是「每个任务都广播」；普通提醒/音量/开程序不会走这条路径（见 §4 逐条回答）。

## 3. 其余机制的证据

### 3.1 提醒/提示/Toast 的前台与合成器操作

`CRemindWnd`（提醒窗口）反编译可见：

- `chkRmdTrans` / `sldRmdAlpha`：透明/分层窗口；
- `DuiLib::CWindowWnd::ShowWindow(..., true, false)`；
- `SetForegroundWindow(hWnd)`（`chkRestoreFocus` 时）；
- `Util::Window::FlashWindowEx(hWnd, ...)`；
- `CRemindWnd::TryPlaySound`：播放提示音。

Toast 路径 `CToastNotifyManger::ShowNotification`（0x6d09ba）：

```c
local_400.uFlags = 0x10;               // NIF_INFO
Shell_NotifyIconW(NIM_ADD, &local_400); // 跨进程调用 Explorer 托盘
```

窗口滑入/滑出使用 `timeSetEvent(0x1e, 0, FUN_006d085b, ...)`（**30ms 一次**），回调里 `SetWindowPos` 每次移动 30px。也就是说每次提醒/提示都会在短时间内连续驱动 DWM/窗口重排，并同步调用 Explorer 的托盘接口。

这类操作本身通常不会冻结整机数秒，但会叠加在机制 A 上：主线程在显示/动画期间不抽钩子消息，输入就会卡顿；托盘/焦点变化会让任务栏和前台应用一起抖动。

### 3.2 运行程序类动作

- zTasker 导入 `Utility.dll!ExecApp` / `ExecAppWithEnv`，内部用 `CreateProcessW`；管理员选项用 `ShellExecuteExW` 的 `runas`。
- `Utility.dll` 还导入 `CreateProcessWithLogonW`（以其他用户运行），属于更重的凭据/会话操作。
- 每次启动新进程都可能触发 Defender 实时扫描（首次/新文件最明显）。本报告未对 Defender 做 ETW 归因，标为「中」。

### 3.3 音量动作

`Volume.dll` 的 `CVolCtrl` 在每次音量动作时构造/析构，`ChangeToVol`（0x100025d0）在 Vista+ 分支：

```c
CoInitialize(NULL);
CoCreateInstance(CLSID_MMDeviceEnumerator, ...);
EnumAudioEndpoints(...);          // 枚举全部音频端点
GetDefaultAudioEndpoint(...);
IAudioEndpointVolume::SetMasterVolumeLevelScalar(...);
CoUninitialize();
```

`GetVol` 走同样的 COM/枚举路径。本机用 `机制验证/audio_probe.cs` 直接调用该 DLL 的导出函数（只 `GetVol`，不改音量）：

| 场景 | 耗时 |
|---|---:|
| 首次 | 19.16 ms |
| 后续 | 3.06–5.03 ms |
| 24 次连发（400ms 间隔）+ 系统延迟探针 | 探针 p99 0.53ms、max 0.99ms，**无可测的系统级尖峰** |

结论：音量动作在本机是 3–19ms 级别，单独不足以让整机卡顿；它的影响主要是「叠加在机制 A 上」以及音频设备多/蓝牙切换时更慢。**不要把它排到主因。**

### 3.4 重型系统动作（仅对应动作）

- `Util::System::EmptyAllWrokSet`（0x10076460）：`CreateToolhelp32Snapshot` 枚举**所有进程**，对每个进程 `SetProcessWorkingSetSize(-1,-1)` + `K32EmptyWorkingSet`。这是「清理内存」动作，会让全系统瞬间大量缺页/回读，卡顿明显。
- `Util::App::RemoveSelfExe` / `DeleteSelf`：自删除辅助进程把自己设为 `REALTIME_PRIORITY_CLASS(0x100)` + `THREAD_PRIORITY_TIME_CRITICAL(0xf)`；`DeleteSelf` 把当前进程设为 HIGH、把 cmd 设为 IDLE，并用 `CREATE_SUSPENDED` 后 `ResumeThread`。
- 主程序导入 `ChangeDisplaySettingsExW`（分辨率切换）、`ExitWindowsEx`（关机/重启）、`BlockInput`（阻断输入）——均为系统级动作。
- `Utility.dll` 的 `WriteBool/SetKey/WriteBool/WriteString` 在写注册表后调用 `RegFlushKey`（同步刷新整个注册表 hive），用于任务管理器/注册表/锁屏等系统设置动作。

### 3.5 每秒条件检查与全量进程枚举（常驻抖动）

本机 4 个 1 秒进程监测任务，加上窗口监测。`ProcessExistsByName` → `GetProcessList` 的实现（`Utility.dll`）使用：

```c
NtQuerySystemInformation(5, buf, 0x100000, &ret);  // SystemProcessInformation，1MB 起，长度不足翻倍
CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);   // 另一条枚举路径
```

本机实测（`机制验证/sys_cost_probe.cs`，x86）：

| 原语 | 平均耗时 |
|---|---:|
| `NtQuerySystemInformation(5, 1MB)` | 4.49–4.62 ms |
| Toolhelp32 进程枚举 | 7.59–7.68 ms |
| WMI `Win32_Process` 查询（对照） | 201.38 ms |

即使没有任务触发，这些监测每秒也会在主线程上产生约 12ms/次的枚举；4 个 1 秒监测合计约 20–50ms/s 的主线程占用。这就是「空闲时也有周期性抖动」的来源。

### 3.6 每次执行保存与日志

- `CTaskData::SaveFile`（0x5bca13）每次保存整个 `Tasks.dat`（当前 212,672 字节），用 `fopen`/`fwrite`/`fclose` 写文件，**没有** `FlushFileBuffers`。
- 日志是逐行追加的文本文件；`FlushFileBuffers` 的 8 个调用点全部在命名管道单实例代码里（0x483160/0x4831c0/0x4831f0/0x483480/0x483680），**不在日志写入路径**。
- 实际日志中 `Save开始`/`Save结束，耗时0ms` 占绝大多数（11-10 风暴期也有大量 0ms），所以「每次全量保存」不是主因，只是磁盘/杀软层面的叠加项。

## 4. 对任务所列 12 条怀疑方向的逐条回答

| # | 怀疑方向 | 结论 | 证据 |
|---|---|---|---|
| 1 | 每次执行是否 `SystemParametersInfo`/`SetSysColors`/`SendMessage(HWND_BROADCAST, WM_SETTINGCHANGE)` | **有，但仅特定动作**：主题（2 次 `SendMessageTimeout` 广播）、鼠标速度/屏保（`SPIF_SENDCHANGE`）。普通提醒/音量/开程序不走 | `SetDarkMode` 0x10076ce0；`SetMousePointerSpeed` 0x10031820；`EnableScreenSaver` 0x10076630；未导入 `SetSysColors` |
| 2 | 每次执行全进程/全窗口枚举 | **进程枚举有**（1 秒监测，主线程；`NtQuerySystemInformation` 1MB + Toolhelp）；**全窗口枚举不在一任务执行路径**（`EnumWindows` 用于托盘/Alt-Tab/窗口列表） | `ProcessExistsByName`/`GetProcessList`；`EnumWindows` 调用点 0x1098ab/0x11b6b7 等 |
| 3 | WMI / `Get-CimInstance` / PowerShell | **代码有，但不在轻任务运行时路径**：`GetCmdlineWMI` 在 `ttGetProcInfo`（获取进程信息）与任务编辑器里；实测 201ms/次，若跑会非常重，但普通执行不调用 | `GetCmdlineWMI` 字符串 xref；`FUN_00691105` 读 `edtGetProcInfoName`；`FUN_006957ef` 读 `optResetProc*` |
| 4 | 每次同步保存 `Tasks.dat`/重写日志/全局锁/`FlushFileBuffers` | **保存有，但 0ms 级**；日志缓冲写，无逐行 flush；任务管理器有全局临界区，但保存很快 | `CTaskData::SaveFile`；日志 `Save结束，耗时0ms`；`FlushFileBuffers` 全在管道代码 |
| 5 | 改优先级/亲和性/工作集 | **仅重型动作**：自删除辅助进程 REALTIME+TIME_CRITICAL；`EmptyAllWrokSet` 只在「清理内存」动作；普通任务不改优先级/亲和性 | `RemoveSelfExe`/`DeleteSelf`；`EmptyAllWrokSet` 0x10076460 |
| 6 | `CreateProcess` 带 `CREATE_SUSPENDED`/调试标志、注入、APC | **仅自删除辅助进程**用 `CREATE_SUSPENDED`+`ResumeThread`；**未导入** `WriteProcessMemory`/`CreateRemoteThread`/`QueueUserAPC` | `DeleteSelf` 0x10001b60；导入表扫描 |

## 5. 明确排除的假设

1. **`timeBeginPeriod(1)` / zTasker 抬高系统定时器分辨率**：未导入 `timeBeginPeriod`；上一轮 `powercfg /energy` 的请求者是 LocalSend/AMD/StarRail，不是 zTasker。**排除**。
2. **每次任务执行都重装全局钩子**：钩子只在 `CTaskListUI::InitWindow` 安装一次。**排除**。
3. **普通任务每次都做 WMI 查询**：`GetCmdlineWMI` 只在 `ttGetProcInfo`/任务编辑器路径；普通提醒/音量/开程序不调用。**排除（对轻任务）**。
4. **普通任务每次都清空所有进程工作集**：`EmptyAllWrokSet` 只由「清理内存」动作的 `chkMemClearProcSet` 触发。**排除（对普通任务）**。
5. **普通任务都改优先级到 HIGH/REALTIME**：`SetPriorityClass`/`SetThreadPriority` 只在自删除辅助函数里；普通动作不变更。**排除**。
6. **每次执行同步 flush 日志**：`FlushFileBuffers` 全在命名管道代码；日志是缓冲写。**排除**。
7. **低级键盘钩子回调本身做重活导致每次按键卡**：回调只做按键匹配并 `PostMessageW(0x804)` 到分发线程；回调本身轻。**但它所在线程被任务阻塞时，问题不在回调内容，而在线程不能抽消息**——这正是主因 A。
8. **32 位进程本身导致全系统卡顿**：WoW64 只增加单进程开销，不能解释跨进程输入延迟。**排除为直接机制**。
9. **`SetSysColors` / 每次执行墙纸广播**：未导入 `SetSysColors`；当前任务列表无墙纸类动作。**排除**。

## 7. 规避与缓解措施（具体到设置项）

### 7.1 降低机制 A 的影响（最有效，但受限于设计）

1. **不要让 zTasker 常驻**：玩游戏/做重活时托盘右键退出。o 退出后全局低级钩子和 1 秒调度都不存在。临时禁用任务不够，因为调度器和钩子仍常驻。
2. **减少复合任务里的「延迟」和「等待窗口」**：这两类动作直接阻塞调度线程。能用「等待窗口出现」事件替代轮询就替代；必须等待时把超时从 5s 降到 1–2s。
3. **不要在任务里放「提醒 + 声音 + 透明 + 恢复焦点」全套**：提醒窗口选项里关闭：
   - 「透明/淡入淡出」(`chkRmdTrans`、`sldRmdAlpha`)
   - 「恢复焦点」(`chkRestoreFocus`)
   - 「闪烁窗口」(`FlashWindowEx`)
   - 提示音（`TryPlaySound`）
4. **关闭托盘动画**：选项/界面 → 托盘动画（`Config.dat` 的 `chkTrayAni=1` 改为 0）。每次任务执行都会 `EVENT_TRAY_TASK_DEC`，动画会反复更新托盘。
5. **热键尽量少**：键盘钩子是无条件安装的，但只要热键表小，回调遍历就轻；鼠标热键关闭可避免 `WH_MOUSE_LL`。

### 7.2 避开机制 B（可直接消除秒级冻结）

1. **不要用 zTasker 做「切换主题」「调鼠标速度」「开关屏保」**：
   - 主题：用 Windows 设置手动切，或接受一次 6 秒冻结；不要让它在游戏/会议前自动执行。
   - 鼠标速度/屏保：用系统设置，不要做成任务。
2. 如果必须保留主题任务，把它安排在离开电脑时执行；不要设置「开机/解锁/前台程序变化」触发。

### 7.3 降低常驻抖动（机制 G）

1. 把所有 1 秒进程/窗口监测改为 **10–30 秒**：
   - 「miui扩展」「结束 miuitools」「关闭周末游戏进程」「登录微信」：`edtProcChkSec`/`edtWndChkSec` 1 → 10。
   - 「重启localsend」「重启NDM」：优先改成「进程退出时」触发，而不是「不存在」轮询。
2. 减少监测任务数量：能合并的合并，能删的删。
3. 检查 `Config.dat` 中 `cmbLogs=30`，定期清理 `User\Logs`（日志本身不是主因，但减少杀软扫描面）。

### 7.4 音量与开程序

1. 音量：优先用键盘音量键/系统 OSD，不要用 zTasker 的 `ttVolume*` 动作（每次 3–19ms 的 COM 枚举，设备多时更久）。
2. 开程序：把常用程序路径加入 Defender 排除项（仅在确认文件可信时）；避免每次任务都启动一个会被扫描的新 exe。
3. 不要用「清理内存」动作（`EmptyAllWrokSet` 会清空所有进程工作集，必然全系统卡）。

### 7.5 升级能否根治？

**不能。** 本报告反编译的是 **2.3.14**（当前最新），其：

- `CTaskListUI::StartTaskTimer` 仍是 1 秒 `WM_TIMER`；
- `CTaskListUI::InitWindow` 仍调用 `CHotKey::Start` 安装全局低级钩子；
- 调度器仍在主线程同步执行动作；
- `SetDarkMode` 仍是 `fuFlags=0` 的双广播；
- 「清理内存」「分辨率」「自删除」等动作实现未变。

2.3.14 新增的「限制触发次数」只能限制任务执行频率，不能改变「执行时阻塞主线程/钩子」的架构。**升级只能减少风暴频率（配合配置），不能根治单次执行的卡顿。**

## 8. 仍未验证的点

1. **没有在 zTasker 进程内抓运行时调用栈/线程 ID**：主因 A 的线程归属是静态调用链 + Win32 语义推断（强，但不是调试器实测）。若要 100% 确认，需要在任务执行瞬间抓 zTasker 主线程栈（如 ETW 采样/调试器），本报告未做。
2. **Defender 对「开程序」的贡献未量化**：未抓 `Microsoft-Windows-Windows Defender/Operational` 或 `MpCmdRun` 事件。
3. **提醒/Toast 动画的实际耗时未逐项计时**：只确认了 `SetForegroundWindow`/`FlashWindowEx`/30ms `SetWindowPos`/`Shell_NotifyIcon(NIF_INFO)` 的代码存在，未在真实提醒任务上测端到端耗时。
4. **2.3.12 与 2.3.14 的线程模型未逐字节比对**：2.3.14 已确认存在相同结构；2.3.12 本机运行的版本未反编译（解包只有 2.3.0/2.3.14），但 2.3.0 与 2.3.14 的导入/定时器模式一致，推断 2.3.12 相同。
5. **`LowLevelHooksTimeout` 未在本机注册表中显式配置**：实测有效阈值约 300–400ms；该值可能随 Windows 版本/策略变化。
6. **鼠标钩子是否当前安装**：`WH_MOUSE_LL` 取决于「禁用鼠标热键」开关（`chkAdvDisMouse`），本机配置未逐项确认；键盘钩子无条件安装。
7. **广播 lParam 指针的跨进程安全性**：`SetDarkMode` 传入的是 `Utility.dll` 地址空间内的非空指针；广播到其他进程时该指针无效。多数应用不解析 lParam，但这是潜在崩溃风险（未观察到崩溃）。
8. **未实测 zTasker 真实任务执行瞬间的端到端输入延迟**：受「不得结束用户 zTasker、不得改用户配置」限制，没有人为触发用户的轻任务；用合成探针复现了机制的各组成部分。2026-11-11 补充的 Suspension A/B 已从运行时证明「主线程 16184 就是全局钩子宿主」（详见 §11），但「真实任务执行」场景因权限拒绝结束/重启 zTasker、替换 `Tasks.dat` 而未跑；`Tasks_test.dat` 已准备好，待用户本人授权即可闭环。
9. **`zTasker.exe -nohk` 未实测**：反编译显示 `CTaskListUI::InitWindow` 在 `FUN_0044c350(L"nohk")` 返回真时跳过 `CHotKey::Start`（及另两个初始化），高概率可完全不装全局钩子；但需要重启 zTasker 才能验证，本次权限未放行。使用前请确认热键/快捷短语可接受失效，并观察托盘/系统状态初始化是否正常。
10. **未抓到任务执行时主线程的等待函数/栈**：可用 `GetThreadWaitChain` 或 ETW 采样补充；本次只做了 Suspension 级别的运行时证明。

### 11.2 主线程 vs 热键线程的 Suspension A/B

探针：`机制验证/input_latency_probe.cs`。它在自己的进程里建一个前台窗口，注入无害 `VK_F24`，测量「注入 → 前台窗口收到 `WM_KEYDOWN`」的延迟；测试期间对目标线程 `SuspendThread`，等待收键后再 `ResumeThread`。

| 场景 | 目标线程 | 阻塞时长 | 收键延迟（3 次） | 平均 |
|---|---:|---:|---|---:|
| 空闲基线 | — | 0 | 31.5–32.1 ms | 31.8 ms |
| Suspend 主 UI | 16184 | 500 ms | 652.1 / 655.1 / 653.5 ms | **653.6 ms** |
| Suspend 主 UI | 16184 | 300 ms | 660.3 / 656.6 / 659.7 ms | **658.8 ms** |
| Suspend 主 UI | 16184 | 700 ms | 655.2 / 660.3 ms | **657.8 ms** |
| Suspend 主 UI | 16184 | 100 ms | 659.7 / 657.5 / 655.6 ms | **657.6 ms** |
| Suspend 热键线程 | 10552 | 500 ms | 33.1 / 31.9 / 32.6 ms | **32.5 ms** |
| Suspend 对照线程 | 33044 | 500 ms | 47.0 / 46.4 / 31.4 ms | 41.6 ms |

结论：

1. **zTasker 的全局键盘钩子确实挂在主 UI 线程 16184 上**：挂起它 → 全系统收键延迟约 650ms；挂起 HotKey 分发线程 10552 或无关线程 → 基本无影响。
2. 在 `SuspendThread` 场景下，即使只挂起 100ms，系统也按钩子超时量级（本机约 650ms）才放行——**一次卡顿就是数百毫秒**。真实任务执行中的普通忙等可能只延迟「忙等时长」，但只要超过钩子超时（约 300–650ms），同样会按超时/丢事件处理。
3. 这直接解释了「任务执行瞬间整个系统卡一下」：任务在主线程执行，主线程一忙，全桌面键鼠就付一次数百毫秒的代价。

### 11.3 空闲时的输入延迟分布

`input_idle20.csv`（20 次，zTasker 空闲、1s 调度器照常运行）：

- p50 = 31.8 ms，p95 = 46.9 ms，max = 46.9 ms，20/20 收到，无超时。
- 基线含探针自身 5ms 轮询开销；重点是与 Suspend 场景的 **650ms** 对比。

主线程 CPU 采样（`thread_cpu_probe.exe 16184 8 thread_cpu_16184.csv`）：

| 秒 | 主线程 16184 单次最大 CPU | 该秒总 CPU |
|---:|---:|---:|
| 0–7 | 15.63–31.25 ms | 15.63–31.25 ms |

即：**即使没有任何任务触发，主 UI/钩子线程每秒也会做约 16–31ms 的活**（进程监测的 1MB `NtQuerySystemInformation` + Toolhelp 枚举）。这就是空闲时周期性抖动的来源；当按键恰好落在这 16–31ms 内，收键会等这段忙完；任务执行时忙得更久，就按钩子超时（数百毫秒）计。

## 12. 根治可行性（三档）

### 12.1 能根治（需要改 zTasker 本身，配置/运行方式做不到）

| 改动点 | 具体做法 | 代价 |
|---|---|---|
| `HotKey.dll!CHotKey::Start` / `FUN_100037f0` | 不在调用线程直接 `SetWindowsHookEx`；创建一个**专用钩子线程**（自带 `GetMessage` 循环），在该线程安装 `WH_KEYBOARD_LL`/`WH_MOUSE_LL`。钩子回调与任务执行彻底解耦 | 小，局部改动；需处理线程退出/重装钩子 |
| `TaskTimerProc` / `FUN_006bd7ce` | 1s `WM_TIMER` 只做条件判断与投递，把动作执行放到 worker 线程（`CTasker` 已有 Wait/事件模型） | 中；需梳理任务状态/取消/并发 |
| `CPostExec::Commit` / `FUN_0042a450` | 把同步 `SendMessageW(hwnd, 0x2B0F)` 改为 `PostMessage`（或异步事件），避免任务线程等 UI 线程 | 小；注意事件顺序/生命周期 |

只要完成第一条（钩子专用线程），机制 A 就根治；后两条进一步消除 UI 线程对任务完成的同步等待。这是给作者最明确、最值得提的反馈。

### 12.2 只能缓解（用户可做，不改二进制）

| 措施 | 效果 | 代价/限制 |
|---|---|---|
| **`zTasker.exe -nohk` 启动** | 高概率跳过 `FUN_006c67fa`（`CHotKey::Start`），从而**完全不安装全局键鼠钩子**；机制 A 消失 | 失去所有热键/快捷短语；`FUN_0044c350(L"nohk")` 的反编译显示它是命令行开关，但**未实测**（需重启，权限未放行）；同分支还会跳过 `FUN_006c8597/FUN_006c925c` 两个初始化，需用户确认无副作用 |
| 关闭托盘动画（`chkTrayAni=0`）、提醒的透明/恢复焦点/闪烁/声音 | 降低机制 C 的 UI/合成器/音频叠加 | 仅减轻，不能消除主线程阻塞 |
| 1s 监测改 10–30s；「不存在」改「退出时」 | 降低机制 G 的常驻 20–50ms/s 主线程占用 | 触发延迟变长 |
| 不用主题/鼠标速度/屏保/音量/清理内存动作 | 避开机制 B/E/6 的秒级冻结 | 功能受限 |
| 游戏/重活时退出 zTasker | 最彻底的用户侧规避 | 任务不执行 |
| 升级 2.3.14 + 触发次数限制 | 只降低风暴频率 | **不改变线程模型，不能根治** |

### 12.3 不可行/不建议

| 方案 | 结论 | 原因 |
|---|---|---|
| 降 zTasker 进程优先级 / 放独立 Job | **不可行** | 钩子线程被自己的任务阻塞，优先级不改变“线程不抽消息” |
| 以服务方式运行 / 独立会话/桌面 | **不可行（对本用途）** | Session 0 不能为用户桌面安装交互式 LL 钩子；独立桌面上的钩子对用户桌面无效；等于放弃热键 |
| DLL 注入 + 在注入线程重装钩子 / Hook `SetWindowsHookEx` | **不建议** | 要移除旧钩子、跨版本维护、易被 AV/反作弊拦截；成本远高于上游改一处 |
| 调大 `LowLevelHooksTimeout` | **不建议** | 只会让每次卡顿更长；调小则更早丢键/摘钩子，都不能消除阻塞 |
| 组策略/注册表“禁用低级钩子” | **不存在可用策略** | 没有官方策略只禁用第三方 LL 钩子而保留功能 |

### 12.4 最省事且收益最大的一条组合

**若不需要 zTasker 热键/快捷短语**：用 `zTasker.exe -nohk` 启动（先小规模验证无副作用）+ 关闭托盘动画 + 1s 监测改 10–30s。  
**若必须保留热键**：退出 zTasker 做游戏/重活；保留 zTasker 只做低频任务；把时间敏感任务交给 Windows 任务计划程序/AHK；同时关闭托盘动画、提醒特效，避免主题/鼠标/屏保/音量/清理内存动作。  
这两套都不改二进制，前者最接近“根治”，后者是“把影响压到可接受”。
