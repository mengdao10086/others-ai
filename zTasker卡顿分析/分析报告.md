# zTasker 卡顿分析报告

> 执行期「轻任务也卡整个系统」的机制分析见 [卡顿机制分析.md](卡顿机制分析.md)。

- 分析日期：2026-11-10
- 目标：解释 zTasker「运行大部分任务时系统明显卡顿」，并给出可执行解决办法
- 本机实际版本：zTasker 2.3.12（安装于 `C:\Users\14986\AppData\Local\zTasker\`）
- 对比版本：2.3.0 安装包（本机） vs 官方当前 2.3.14（2.3.13 已下架，见 §1）

## 0. 结论速览

按证据强度与影响排序：

| 排名 | 根因 | 证据强度 | 影响 | 版本相关？ |
|---|---|---|---|---|
| 1 | 任务「重启localsend」配置成“进程不存在→每秒触发”，且等待窗口失败后**跳回动作1**，形成无冷却的失败重试闭环；其程序路径仍指向已不存在的 `LocalSend-1.14.0` | 强（日志最高 3460 次/小时、路径、任务 XML 全部对上） | 任务几乎 100% 时间在跑，持续创建进程、枚举窗口、写日志、刷新 UI | 用户配置；但“无冷却”是设计固有 |
| 2 | 进程/窗口监测按 1 秒间隔轮询；进程检查每次用 **1MB 缓冲 + NtQuerySystemInformation** 全量枚举系统进程 | 强（任务配置 1s + Utility.dll 反编译） | 本机 5 个 1s 监测同时存在，空闲时也有约每 1.2 秒一次 16–31ms 的 CPU 尖峰 | 设计固有（2.3.0 起相同） |
| 3 | 每次任务执行都会全量保存 `Tasks.dat`（212KB）并逐条写日志；日志在异常循环下可达 4.5MB/小时 | 中强（日志统计 + 保存耗时记录） | 磁盘写、杀软扫描、UI 卡顿；2.3.12 曾在风暴后堆损坏崩溃 | 设计固有；2.3.11/2.3.13 有日志改进 |
| 4 | 常驻低级键盘钩子 `WH_KEYBOARD_LL`，鼠标热键开启时再加 `WH_MOUSE_LL` | 中（Ghidra 常量确认） | 回调本身很轻（仅按键/点击时处理，鼠标移动直接放行），不是主因 | 设计固有 |
| 5 | UI/托盘动画、任务状态事件在每次执行时刷新 | 弱（日志可见 EVENT_TASK_STAT / 托盘动画） | 轻微，放大第 1 条的体感 | 设计固有 |

**明确排除/证据不足：**

- `timeBeginPeriod(1)`：zTasker 主程序与 Utility.dll 都**没有导入** `timeBeginPeriod`；能源报告显示当前 1ms 定时器分辨率由 `localsend_app.exe`、AMD `AMDRSSrcExt.exe`、`StarRail.exe`、`HYPHelper.exe` 请求，**不是 zTasker**。
- 屏幕截图/OCR/硬件监控轮询：代码存在（BitBlt、ScrCap.dll、OpenCV、PDH、NtQuerySystemInformation），但当前 22 个任务里没有启用这类触发/动作。
- 自更新检查：频率很低（配置 `lastUpdateCheck=2026-04-10`），不是卡顿源。
- UI 线程阻塞/跨线程 `SendMessage`：存在跨线程消息，但未找到阻塞主线程的直接证据，标记「证据不足」。

**最推荐的三条措施：**

1. 修正或禁用「重启localsend」任务，并把“等待窗口失败”从「跳转到动作1」改为「中断复合任务流程」。
2. 把所有 1 秒的进程/窗口监测间隔改为 10–30 秒；能用“退出时”触发就不要用“不存在”触发。
3. 升级到 2.3.14，用新增的「限制计数的触发次数（每小时/每天）」给这类任务加上限。

## 3. 关键证据与根因

### 3.1 根因 1：任务「重启localsend」形成每秒失败重试闭环（主导）

#### 任务配置

`User\Tasks.dat` 中任务 `876-YTCN4I9LJA`（名称「重启localsend」）：

- 类型：`ttMultiTasker`（复合任务），启用状态 `Stopped=0`。
- 触发：`SchType=21`（进程监测），监测 `localsend_app.exe`，条件文案「不存在」，`edtProcChkSec=1`（每 1 秒检查一次）。
- 动作链：
  1. `ttExec` 运行程序，路径 `C:\Program Files\LocalSend-1.14.0\localsend_app.exe`（**不存在**；实际安装为 `C:\Program Files\LocalSend\localsend_app.exe`）。
  2. 延迟 `1000ms`。
  3. 等待窗口：class `FLUTTER_RUNNER_WIN32_WINDOW`、title `LocalSend`，超时 `5` 秒。
  4. 等待失败时选择 **跳转到动作 1（ID 47）**（`cmbWinWaitMatch2=2`）。
  5. 关闭 LocalSend 窗口。

由于第 1 步永远失败、第 4 步又跳回第 1 步，复合任务内部形成无冷却循环；任务结束后，1 秒进程监测发现 LocalSend 仍不存在，立即再次触发。结果就是**几乎 100% 时间都在执行这个任务**。

#### 日志统计（强证据）

|---|---:|---:|---:|---:|---:|---|
| 2026-11-05 | 4,484,444 B | 45,389 | 3,460 | 3,452 | 3,352 | 约 58 分钟连续风暴 |
| 2026-11-10 | 1,076,109 B | 10,719 | 900 | 892 | 780 | 约 13 分钟风暴 |
| 平常日 | 20–230 KB | — | — | — | — | 对比基准 |

原始失败行（逐字）：

```text

```

任务启动节奏约 1 秒一次：


每次尝试约产生 13 行日志、约 1.3KB。风暴期间日志写入速率的量级为 13 行/秒、1.3KB/秒。

#### 为什么 LocalSend 在跑时就不卡

当前 `localsend_app.exe`（PID 9096）已运行，任务 876 的“进程不存在”条件不成立，风暴停止；日志最后一次写入停在 20:28:15。可复现验证：

- 打开 zTasker 日志窗口，若看到大量 `运行失败:...LocalSend-1.14.0...` 和 `等待窗口超时`，且日志每分钟增长数百 KB，即为本条。
- 关闭 LocalSend 后观察，卡顿应立即出现；重新启动 LocalSend 后消失。

### 3.2 根因 2：1 秒监测 + 全量进程枚举（设计固有）

#### 本机启用的监测型任务

| 任务 ID | 名称 | 触发类型 | 检测间隔 | 条件 |
|---|---|---|---:|---|
| 672-PUN1C2KA88 | miui扩展 | 进程监测（SchType 21） | 1s | 出现（create），miuitools.exe |
| 932 | （结束进程） | 进程监测 | 1s | 退出（quit），miuitools.exe |
| 876-YTCN4I9LJA | 重启localsend | 进程监测 | 1s | 不存在，localsend_app.exe |
| 885-Y48RU6JVQT | 重启NDM | 进程监测 | 5s | 不存在，NDM1.4.20.exe |
| 123-MBN20IVSXZ | 关闭周末游戏进程 | 进程监测 | 1s | 出现（create），Endfield.exe |
| 834-RJ99PFQ10X | 登录微信 | 窗口监测（SchType 22） | 1s | 出现，WeChatLoginWndForPC |

即：4 个进程监测以 1 秒、1 个以 5 秒、1 个窗口监测以 1 秒运行。即使没有任何任务真正触发，这些监测线程也会按间隔醒来。

#### 进程检查的实现代价

`Utility.dll` 的 `Util::Process::GetUniqueProcessList`（Ghidra，地址 0x10046a40）逻辑：

```c
uVar10 = 0x100000;                       // 初始 1 MB
FUN_1004d4b0(&local_26c, 0x100000);
iVar2 = NtQuerySystemInformation(5, local_26c, 0x100000, &local_274);  // 5 = SystemProcessInformation
while (iVar2 == -0x3ffffffc) {           // STATUS_INFO_LENGTH_MISMATCH
    uVar10 = uVar10 * 2;                 // 缓冲翻倍
    FUN_1004dbe0(&local_26c, uVar10);
    iVar2 = NtQuerySystemInformation(5, local_26c, uVar10, &local_274);
}
```

同时 `Utility.dll` 还使用：

```c
CreateToolhelp32Snapshot(2, 0);   // TH32CS_SNAPPROCESS
Process32FirstW(...); Process32NextW(...);
```

也就是说，**进程存在性检查会向内核查询完整系统进程信息（默认 1MB 缓冲）并遍历**（进程监测调用该枚举为高度可能，见 §6 第 4 条）。4 个 1 秒监测 = 每秒最多 4 次 1MB 级内核缓冲分配/拷贝；在游戏等高负载场景下会放大页错误与 CPU 抢占。

#### 动态侧证

空闲采样（PID 13028，200ms 间隔取 CPU 时间增量）：

```text
0 31 0 0 0 0 16 0 0 0 0 16 0 0 0 0 16 0 0 0 0 16 ...
```

即约每 1.2 秒出现一次 16–31ms 的 CPU 尖峰，和 1 秒监测/UI 定时器节奏一致；空闲平均约占单核 1.3%。这不是“明显卡顿”的全部，但它解释了为什么 zTasker 常驻时系统始终有周期性抖动。

### 3.3 根因 3：每次执行全量保存 + 高频日志（设计固有）

- 每次任务运行都会触发 `Save开始 / Save结束`：2026-11-10 日志中 124 次复合任务执行对应 127 次保存。
- `Tasks.dat` 当前 212,675 字节；保存耗时统计（全部日志，2,770 次 `Save结束，耗时Nms`）：
  - ≥100ms：279 次
  - ≥500ms：74 次
  - ≥1000ms：23 次
  - 最大 2,313ms
- 日志为逐行追加的文本文件（`User\Logs\YYYY-MM-DD.log`），风暴时约 13 行/秒。主程序导入了 `FlushFileBuffers`（7 处调用），但其中多处位于命名管道代码，**未能证明日志逐行强制刷盘**；因此“同步 flush”标为「部分证据」。
- 2.3.0 → 2.3.13 的日志改进：2.3.9「日志系统全面改进，改善稳定性和性能」；2.3.11「减小日志量」；2.3.13「修复了几个日志系统带来的崩溃问题」。日志量有改善，但本次风暴仍达 4.5MB/小时。

### 3.4 根因 4：低级键鼠钩子（有钩子，但负载轻）

`HotKey.dll` 的 Ghidra 反编译结果（地址 0x100037f0）：

```c
DAT_1000b498 = SetWindowsHookExW(0xd, FUN_100057d0, DAT_1000b490, 0);  // 13 = WH_KEYBOARD_LL
if (cVar1 != 0) {
    DAT_1000b494 = SetWindowsHookExW(0xe, FUN_10005620, DAT_1000b490, 0);  // 14 = WH_MOUSE_LL
}
```

- 键盘钩子是**无条件安装**的全局低级钩子；鼠标钩子按开关安装。
- 回调分析：
  - 键盘回调只在 `WM_KEYDOWN/WM_SYSKEYDOWN` 时做双击判定、遍历热键表并分发；不是每条消息都做重活。
  - 鼠标回调对 `WM_MOUSEMOVE`（0x200）直接跳过，只处理点击/滚轮，并调用 `GetAsyncKeyState` 读修饰键。
- 结论：钩子存在，但回调轻量，**不是主因**；在高回报率鼠标 + 高负载游戏下会有少量输入路径开销。

### 3.5 定时器与系统分辨率

- 主程序 IAT 调用点常量：
  - `SetTimer(..., 0x1F4, ...)`：**500ms**，两处（0x6A384、0x6B92C）。
  - `SetTimer(..., 0xBB8, ...)`：**3000ms**，一处（0xADBEE），附近字符串 `_zTasker_ToTrayIcon_Message_Window_`，与托盘相关。
  - 2.3.0 另有一处带 `50`（ms）立即数参数的疑似 `SetTimer` 调用点（0x290B7F）；该调用点的完整上下文未反编译确认，仅作线索。
  - `timeSetEvent(0x1E, 0, callback, ..., 1)`：**30ms 一次性**定时器，多处，邻近字符串为 UI 按钮（maxbtn/restorebtn），属于 UI 动画/交互，不是全局轮询。
- **没有** `timeBeginPeriod` 导入。
- 系统当前定时器分辨率 1.000ms（默认 15.625ms）。`powercfg /energy` 归因：
  - `\Program Files\LocalSend\localsend_app.exe`（PID 9096）
  - `\Program Files\AMD\CNext\CNext\AMDRSSrcExt.exe`
  - `\Device\HarddiskVolume4\Star Rail\Game\StarRail.exe`
  - `\Program Files\miHoYo Launcher\...\HYPHelper.exe`
  - **报告中没有任何 zTasker 条目**。

因此「zTasker 抬高系统定时器分辨率」这一假设**不成立**（至少当前不是它）。

### 3.6 其余假设

| 假设 | 结论 | 证据 |
|---|---|---|
| 全局定时器/轮询频率过高 | **有（中）** | 1s 监测线程 + 500ms UI 定时器 + 空闲每 1.2s 的 16–31ms CPU 尖峰 |
| `timeBeginPeriod(1)` | **无/证据不足** | 无导入；能源报告请求者为 LocalSend/AMD/StarRail |
| 低级键鼠钩子回调做重活 | **有钩子，但回调轻** | WH_KEYBOARD_LL 常驻；回调仅按键/点击处理 |
| 每任务启动 cmd/powershell/ahk 并同步等待 | **部分有** | `ttExec` 用 `CreateProcessW`；风暴中 892 次启动尝试；未发现每个动作都起 AHK（`Insure ahk env` 仅在启动时出现） |
| 日志同步 flush / 高频写盘 | **部分证据** | 4.5MB/小时、13 行/秒、每次执行全量保存；逐行 FlushFileBuffers 未证实 |
| UI 线程阻塞、跨线程 SendMessage | **证据不足** | 存在 `SendMessageW`/`SendMessageTimeoutW`（异步任务窗口、目录监控），未见阻塞主线程直接证据 |

### 4.3 结论

- **稳定性：改善。** 2.3.9/2.3.11 改进了日志系统并降低日志量；2.3.13 修复日志系统导致的崩溃。本机 2.3.12 的 `0xc0000374` 堆损坏崩溃，2.3.13 起应有改善。

## 5. 解决办法

### 5.1 用户可改的设置（按优先级）

#### 措施 1：修复「重启localsend」任务（最高优先）

操作路径（zTasker 主窗口）：

1. 任务列表 → 选中「重启localsend」→ 编辑。
2. 进入复合任务编辑 → 第 1 个动作「运行程序」→ 把程序路径从
   `C:\Program Files\LocalSend-1.14.0\localsend_app.exe`
   改为
   `C:\Program Files\LocalSend\localsend_app.exe`。
3. 进入「等待窗口」动作 → 把「等待窗口失败时」从 **跳转到动作 1（运行程序）** 改为 **中断复合任务流程**。这样即使路径再失效，也只会失败一次，不会每秒重试。
4. 保存后，在任务列表右键 → 测试运行一次，确认 LocalSend 能启动且窗口能被识别。

如果暂时不需要自动重启 LocalSend：直接**禁用或删除**该任务（任务列表右键 → 禁用任务计划）。LocalSend 本身已有 HKCU Run 自启动项。

#### 措施 2：把 1 秒监测间隔改大，并优先用“退出时”触发

对以下任务逐个编辑 → 计划/自动触发 → 进程监测：

- 「重启localsend」：条件「不存在」→ 改为「退出」；检测间隔 `1` → `10` 或 `30` 秒。
- 672「miui扩展」：检测间隔 `1` → `10` 秒（“出现”条件本身只会在进程启动时触发一次，但后台仍每秒扫描）。
- 932（结束 miuitools）：检测间隔 `1` → `10` 秒。
- 123「关闭周末游戏进程」：检测间隔 `1` → `10` 秒。
- 885「重启NDM」：检测间隔 `5` → `10` 或 `30` 秒（该任务同样是“不存在→启动”，若 NDM 路径失效会以 5 秒周期重试）。
- 834「登录微信」：窗口监测间隔 `1` → `5` 或 `10` 秒（微信登录窗口出现的延迟可接受）。

原则：**能用“进程退出/窗口出现”一次性触发，就不要用“持续不存在/持续存在”轮询**；必须轮询时，间隔 ≥10 秒。

#### 措施 3：升级到 2.3.14 并使用触发次数限制

1. 先备份 `C:\Users\14986\AppData\Local\zTasker\User`（整个目录复制一份）。
2. 退出当前 zTasker（托盘右键 → 退出），运行 `zTasker_2.3.14_Setup.exe` 覆盖安装。
3. 对高风险任务（如「重启localsend」「重启NDM」）：
   任务编辑 → 高级选项 → 「限制计数的触发次数」→ 选择「每小时」或「每天」→ 设置上限（例如每小时 3 次、每天 20 次）。
4. 该功能是 2.3.14 新增，2.3.13 没有；由于 2.3.13 已下架，直接升级 2.3.14。

#### 措施 4：减少钩子与 UI 刷新

- 选项 → 热键：关闭不用的全局热键，尤其是鼠标热键/边角触发；这能避免安装 `WH_MOUSE_LL`，并减少键盘钩子回调里的热键表遍历。
- 选项 → 界面显示：关闭「托盘动画」（配置键 `chkTrayAni`，当前为 1）。每次任务执行都会触发托盘动画/状态事件。
- 选项 → 界面显示：关闭不必要的任务列表自动刷新/提示。

#### 措施 5：控制日志与杀软扫描

- 在 `Config.dat` 中未见日志级别/关闭日志的开关（只有 `chkLogEmbed`、`chkClearLogs`、`cmbLogs=30` 保留天数）。可做的：
  - 在选项里把与日志保留/清理相关的天数调小（配置键 `cmbLogs`，当前 30 天）。
  - 定期清理 `C:\Users\14986\AppData\Local\zTasker\User\Logs\*.log`。
- 可选：把 `C:\Users\14986\AppData\Local\zTasker\User\Logs` 加入 Windows Defender 排除项，降低逐条日志写入被实时扫描的开销。**这会降低该目录的安全防护，仅在确认日志内容可信时使用。**
- 修复 HKCU Run 的过期项（可选但推荐）：删除
  `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run\localsend_app`
  （值为 `C:\Program Files\LocalSend-1.14.0\localsend_app.exe`），保留正确的 `LocalSend` 项。这样开机不会再尝试启动不存在的旧路径。

#### 措施 6：游戏/高负载时暂停 zTasker

托盘右键 → 暂停/退出 zTasker，或临时禁用所有高频任务。对于“玩游戏时明显卡顿”的场景，这是最直接、可逆的验证手段：退出后若卡顿消失，再按上述措施逐项恢复。

### 5.2 无法改只能规避的部分

1. **监测最小粒度与全量枚举**：进程监测按间隔醒来，每次通过 `NtQuerySystemInformation(SystemProcessInformation)` + 1MB 缓冲全量枚举。除非改源码，无法改成“事件驱动”或“只查目标进程”。规避：减少监测任务数量、把间隔调大。
2. **失败重试无自动退避**：2.3.12 及更早版本没有“失败后冷却”；2.3.14 只有次数上限，没有指数退避。规避：把“等待失败”改为中断，或修正路径。
3. **每次执行全量保存 `Tasks.dat`**：任务状态（LastRunTime/NextRunTime）变化即保存整个 XML。规避：避免高频任务；把任务文件放在 SSD 上；减少任务数量/体积。
4. **日志始终开启**：没有日志级别开关。规避：减少触发频率、定期清理、杀软排除。
5. **低级键盘钩子常驻**：只要启用热键就会安装 `WH_KEYBOARD_LL`。规避：不用热键时在选项里关闭；不要在游戏中保留大量热键。
6. **2.3.0 老版本**：日志系统更旧、日志量更大，且有已知崩溃修复缺失。规避：不要停留在 2.3.0，升级到 2.3.14。

## 6. 风险与未验证项

1. **2.3.13 未取得**：官方 404，无法校验任务给出的 SHA256；本报告用 2.3.14 代偿。2.3.13 与 2.3.14 仅隔 3 天，核心轮询代码预计一致，但未逐字节对比。
2. **未做受控性能基准**：没有在隔离环境分别运行 2.3.0/2.3.13/2.3.14 并测量每任务 CPU/IO；版本“快慢”结论仅为静态与日志推断。
3. **风暴期间 CPU 未直接采样**：风暴发生在 11-05 与 11-10，分析时已结束；CPU 影响由日志频率、进程创建次数、保存/写入量推断。
4. **进程监测→`GetUniqueProcessList` 的调用链为高度可能，非动态确认**：`Utility.dll` 中确认了 1MB 全量枚举实现，但未对运行中的 zTasker 做 API 级跟踪（如 ETW/API Monitor）。
5. **日志是否逐行 `FlushFileBuffers` 未证实**：`FlushFileBuffers` 调用点多在命名管道附近；日志可能由 C++ 流缓冲写入。
6. **鼠标钩子是否当前安装未确认**：`WH_MOUSE_LL` 仅在 `cVar1 != 0` 时安装，取决于鼠标热键设置；`WH_KEYBOARD_LL` 是无条件安装。
7. **两个实例的关系未完全确认**：计划任务拉起的 `-m -autorun` 实例（PID 7936）仅剩 1 线程/0.8MB，疑似残留；是否与手动实例重复执行任务、是否由 11-05 崩溃导致，未能确认。建议重启系统后只保留一个实例再观察。
8. **2.3.14 的“触发次数限制”实际拦截效果未实测**：功能来自官方更新日志，未在运行实例上验证。
