# 上机指南（dex2oat-boost）

> 两条路**完全独立**、**二选一**即可；同时启用会让同一次安装被重复编译一次（无害但浪费 CPU/IO）。
> 选路与原理、产物路径见 [`README.md`](README.md)（本指南不重复）。
> 各方案的编译 / 打包 / 配置项 / 设计取舍在各自目录的 `README.md`（本指南不重复）。
> 两方案均**未在目标设备完整真机验证**——各节末尾的〈未验证项〉逐条列明。

## 统一前置

- 设备**已 root**（KernelSU 或 Magisk 其一）。
- **系统与 ROM**：需 Android 15+（方案 A 的 ① 降档依赖 `setDexoptCompilerFilter`；<15 时 ① 失效但无害，②③ 照常），且 ROM 带 MIUI 安装器（`pm path com.miui.packageinstaller` 非空；为空则方案 A 不适用）。目标 ROM 为 Android 16（SDK 36）。
- 一个 **su 终端**（Termux / MT 管理器终端 / `adb shell` + `su` 均可）。
- 一个**测试 APK**（任意小 APK；可直接拿方案 A 自己的 `app-release.apk` 当被测包）。
- 通用复核命令（两条路都用它看装后档位）：
  ```
  dumpsys package <被测包名> | grep -i dexopt
  ```
  期望出现该包处于 `speed` 相关（不同 ROM 字段名略异，找 `filter=speed` / `[status=speed]` 之类）。

## 方案 A · LSPosed 模块

产物：`lsp模块/app/build/outputs/apk/release/app-release.apk`（Edge 落地名 `dex2oat-boost-v1.0.apk`）。

### A-1　安装 APK

```bash
adb install -r "D:/下载/Claude Code/杂项/dex2oat-boost/lsp模块/app/build/outputs/apk/release/app-release.apk"
# 或手机端点装 Edge\dex2oat-boost-v1.0.apk
```
- **期望**：`Success`（或手机上提示已安装）。
- **不符**：`INSTALL_FAILED_*` → 看是 minSdk（28）/ 架构不符；`adb` 不可用则直接在手机上装。

### A-2　LSPosed 里启用模块，作用域只勾安装器

**LSPosed 管理器 → 模块 → dex2oat boost**：
1. 打开**启用**开关；
2. 「作用域」里**只勾**「**应用包管理组件**」（`com.miui.packageinstaller`）。
- **期望**：开关打开，作用域里只有安装器一项。
- **不符**：模块列表里找不到本模块 → 多半没装成功 / LSPosed 未扫到 → 重装 APK 并重开 LSPosed 管理器。

### A-3　给**安装器**授权 root（关键）

在 **KernelSU 超级用户 / Magisk 授权**列表里，给 **`com.miui.packageinstaller`（应用包管理组件）** 授权 root。
- **只需给安装器授权**；模块 APK `com.mengdao.dex2oatboost` **不需要、也无法从授权获益**（模块无自有进程，代码只被注入到安装器进程执行，唯一的 root 动作是安装器进程内发起的 `su`）。
- **期望**：安装器出现在授权列表且为「已授权」。
- **不符**：只授了模块、没授安装器 → 装包后会看到 `③ root 降级失败/无 root…`，按 A-6/处置。

### A-4　重启安装器进程

```bash
adb shell am force-stop com.miui.packageinstaller
```
（或手机设置里强停「应用包管理组件」。）
- **期望**：下次安装从零重新注入模块。
- **不符**：不做 → 当前进程可能仍是旧的、无注入 → A-6 看不到注入行。

### A-5　挂上日志、装一个测试包

```bash
adb logcat -c
adb logcat | grep -i "dex2oatboost"
```
保持监听，然后经 **MIUI 安装器**装一个测试 APK（`adb install -r <测试.apk>` 或手机点装）。
- **期望**：先出注入行，再出 ①②③（见 A-6）。
- **不符**：一行都没有 → 模块未注入 → 回 A-2 / A-4。

### A-6　看四行关键输出（核心判定）

**第 0 行——注入确认**（有它才谈得上后面）：
```
Dex2OatBoost: handleLoadPackage pkg=com.miui.packageinstaller process=com.miui.packageinstaller sdk=36
```
- **无此行** → 未注入 → 回 A-2 / A-4；或跑一次诊断脚本（见下）。

装完测试包后，按**出现顺序**判：

| 关键行 | 含义 | 不符时说明什么 / 该走哪条 |
|---|---|---|
| `① 安装期降档 verify 已设置 (pkg=…)` | ① 成功 ✔ | 若为 `① setDexoptCompilerFilter 不可用/失败，本次不降档 (pkg=…)` → 设备 <Android 15 或隐藏 API 被拦；**① 失效但无害**，② 照常，继续看下一行 |
| `② 调用方对照: sdk=… myUid=… callingUid=… pkg=… installingPkg=… initiatingPkg=… installerUid=…` | ② 已开始，并附判定数据 | 连这行都没有 → ② 未启动 → 看有没有 `安装完成: <pkg> → 触发重编译`；没有则完成信号（广播）未到 → 安装器进程是否被杀，回 A-2 |
| `② 零 root 重编译成功: <pkg> -> speed` | ② 成功 ✔（理想，**零 root**） | —— |
| `② SecurityException，转 root 降级: <pkg> \| java.lang.SecurityException: …` | ② 被系统拒绝 → 自动走 ③ | **本目标 ROM（A16）的预期**：根因是 dexopt 执行期的**应用休眠门禁** `MANAGE_APP_HIBERNATION`（保护级 `signature\|installer`，**不可授予**），② 的零 root 路径在本 ROM 不成立 → 靠 ③；**确认已在 A-3 给安装器授权 root** |
| `③ root 降级重编译成功: <pkg>` | ③ 成功 ✔（依赖安装器已授 root） | —— |
| `③ root 降级失败/无 root，交由系统 bg-dexopt 兜底: <pkg>` | 没给安装器 root，或 su 被拒 | 去 A-3 给 `com.miui.packageinstaller` 授权 root，强停安装器（A-4）后重试 |
| `③ root 通道异常（…）` / 紧随的 `root 降级执行异常: …` | su 不可用 / 执行异常 | 看紧随的 `③ su 诊断: PATH=… whichSu=… 候选: …` 行，定位 su 是否在 PATH、候选绝对路径是否存在可执行 |

> 另有一条 `② 零 root 路径异常，转 root 降级: <pkg> | java.lang.NoSuchMethodException: …`：`performDexOptMode` 签名未识别（该 ROM 改了签名）→ 自动走 ③，功能不受影响，但属「待真机补签名分支」项（见 A〈未验证项〉5）。

**一键采集（可选，手机 su 终端内）：**
```bash
su
sh "/storage/emulated/0/一键另存/测试/dex2oat-boost测试.sh"
```
脚本会在中途提示「去装一个 APK、装完回车」，然后汇总「模块装没装上 / LSPosed 认没认到 / 有没有注入安装器进程」并导出结果。
- 输出：脚本**同目录**的 `dex2oat-boost结果.log`，原始日志在**同目录** `_scratch/dex2oat-boost原始日志.txt`。
- 副本：仓库 `dex2oat-boost测试.sh`；`D:\下载\Edge\dex2oat-boost测试.sh`。
- 手机端建议放 `/storage/emulated/0/一键另存/测试/`。

### A-7　复核装后档位

```bash
adb shell dumpsys package <被测包名> | grep -i dexopt
```
- **期望**：该包处于 `speed` 相关。
- **不符**：仍是 `verify` / `speed-profile` → ②③ 都没落成 → 回 A-6 定分支（是「休眠门禁 + 无 root」还是「签名未识别」）。
- 补充（**会真的重编译一次**，仅需要时用）：
  ```bash
  adb shell pm compile -m speed -f -v <被测包名>   # 期望 final actualCompilerFilter=speed
  ```

### A-8　卸载 / 回滚

```bash
adb shell am force-stop com.miui.packageinstaller
adb uninstall com.mengdao.dex2oatboost
```
或在 LSPosed 管理器里**关闭本模块开关**并重启安装器；同时在 KernelSU/Magisk 里**撤销安装器的 root 授权**。
回滚后：安装期档位恢复系统默认（`pm.dexopt.install`，通常 `speed-profile`）；已编译过的包保持 `speed`，如需还原可 `adb shell pm compile -m speed-profile -f <pkg>`（或 `--reset`）。无持久化残留。

### 方案 A · 已知未在真机验证的项

（来源：实施报告 / 验证报告 / ② 权限链核实，如实声明。）

1. **未做完整真机验证**：是否降档、② 是否成功、③ 是否触发，均未在目标设备完整实测。
2. **② 的零 root 路径在本目标 ROM（A16）已确认被休眠门禁拒绝**（`MANAGE_APP_HIBERNATION`，`signature|installer` 不可授予），实际依赖 ③；③ 能否成功取决于是否给安装器授 root，**待真机验证**。
3. `setDexoptCompilerFilter` 在 Android 16 是否同名同签名：A15 源码有、A16 镜像已核，未在目标 ROM 逐版本实测。
4. `performDexOptMode` 的实际签名：按 A15 AIDL 实现、运行期按方法表解析，未在目标 ROM 逐版本验证（不符会落 ③）。
5. `ACTION_PACKAGE_ADDED / REPLACED` 的送达时机：依赖安装器进程在装完当时存活（杀进程则收不到；本模块不做 commit 兜底）。
6. `sourceCompatibility=1.8` 是本机 JDK 21 的编译适配，非设计选择。
7. 「与方案 C 同启会重复编译」为两版各自独立触发的推断，未做双端并存真机对照。

### 方案 A · 出问题先看哪里

1. **先确认「模块有没有进安装器进程」**——`handleLoadPackage pkg=com.miui.packageinstaller` 是总前提；没有就查 LSPosed 启用 / 作用域 / 安装器进程是否重启 / APK 是否真的装上（`pm path com.mengdao.dex2oatboost`）。
2. 跑一次 `dex2oat-boost测试.sh`，拿到「注入 + 配置库 + 全量日志」的汇总。
3. 再看 ①②③ 四行日志定分支（见 A-6 表）。
4. 最后 `dumpsys package <pkg> | grep -i dexopt` 复核档位。

**常见卡点速查：**

| 症状 | 最可能原因 | 处置 |
|---|---|---|
| 日志一行都没有（无 `handleLoadPackage`） | 作用域没勾 / 安装器进程没重启 | 回 A-2 / A-4 |
| 有 ① 无 `安装完成:` 行 | 安装完成广播未送达（装完那一刻安装器进程被杀） | 回 A-2；本模块**不做 commit 兜底**，杀进程后收不到信号属已知局限 |
| ② 恒 `SecurityException` → ③ | 该 ROM dexopt 执行期有应用休眠门禁（**本目标 ROM 即此**） | 有 root 走 ③（A-3 授权安装器）；无 root 需另评估 |
| ② 恒 `NoSuchMethodException` | `performDexOptMode` 签名与该 ROM 不符 | 自动落 ③；若要零 root 需按真机方法表补签名分支（见 A〈未验证项〉4） |
| `pm compile … -v` 显示 `actualCompilerFilter` 非 speed | ②③ 均未成功 | 回 A-6 定分支 |

## 方案 C · 纯 root / Magisk 模块

产物：`magisk模块/产物/dex2oat-boost-magisk.zip`（md5 `e879b7a86e8041a6fa94b6f904af4349`）。

### C-1　刷入 zip

**Magisk / KernelSU 管理器 → 模块 → 从本地安装**，选 `dex2oat-boost-magisk.zip`。
- **期望**：刷入无报错，模块列表出现 `dex2oat-boost`。
- **不符**：报错 → 确认 zip 完整（md5 见上），换管理器版本重试。

### C-2　重启设备

- **期望**：重启后属性设置与守护进程一起生效。
- **不符**：不重启 → 属性未写、守护未跑（见 C-3 / C-4）。

### C-3　核对降档属性

```bash
su -c 'getprop pm.dexopt.install'
su -c 'getprop pm.dexopt.install-fast'
```
- **期望**：均输出 `skip`。
- **不符**：
  - 仍是系统默认（通常 `speed-profile`）→ 看守护日志有无 `属性 pm.dexopt.install：…->…` 或 `属性 pm.dexopt.install 设置失败（当前 '…'，目标 'skip'）`——后者是 `resetprop`/`setprop` 都被 SELinux 拒，属待真机确认项，本期无解；
  - 完全没这行 → 守护没起来 → 看 C-4 与 `service.log`。

### C-4　核对守护进程

```bash
su -c 'ps -A | grep dex2oat-boost-daemon'
```
- **期望**：有一个 `dex2oat-boost-daemon.sh` 进程。
- **不符**：没有 → 看门狗没起来 → 先确认 `su -c 'getprop sys.boot_completed'` 为 `1`，再看：
  ```bash
  su -c 'tail -n 50 /data/adb/dex2oat-boost/service.log'
  ```
  应含「开机完成，启动守护进程」；若含「守护进程退出（rc=…），5 秒后重启」则守护反复崩，查主日志（C-6）。

### C-5　装一个测试包

经任意方式装上测试 APK（`adb install -r <测试.apk>` 或手机点装），等 **15~30 秒**（轮询 + 3 周期倒计时 + 编译）。
- **期望**：C-6 日志出现该包。
- **注意**：守护**首次运行只建立基线、不编译任何既有应用**；只有「基线之后新出现 / 变更」的包才会编译。**必须在模块跑起来之后再装**测试包。

### C-6　看守护日志

```bash
su -c 'tail -n 50 /data/adb/dex2oat-boost/dex2oat-boost.log'
```
- **期望**出现：
  ```
  已重编译 <被测包名> -> speed（<父目录>/<包名>-<hash>）
  ```
- **不符**：
  - 只有 `首次运行/基线无效：建立基线，记入 N 项，本次不编译任何包` → 是首轮建基线，**属正常**；**在它之后再装一次**测试包。
  - 有 `等待就绪 <pkg>（第 N 轮，pm 路径未指向 <leaf>）` → 覆盖安装的就绪门禁在等 `pm path` 切到新目录，属正常等待（最多 10 分钟），**不是失败**。
  - 完全没提到测试包 → 确认是「模块生效之后才装的」；再确认包目录已在 `/data/app`（`su -c 'ls /data/app'`）。

### C-7　复核装后档位

```bash
su -c 'dumpsys package <被测包名> | grep -i dexopt'
# 或
su -c 'cmd package dump <被测包名> | grep -i filter'
```
- **期望**：该包处于 `speed` 相关。
- **不符**：仍 `verify` / `speed-profile` → 没被重编译 → 回 C-6。

### C-8　卸载与属性还原

管理器里卸载模块，或运行 `uninstall.sh`。卸载会：停守护与看门狗、把降档属性还原为**本次开机记录的原值**（在 `/data/adb/dex2oat-boost/orig_props.txt`，仅当前这次开机有效）、删 `/data/adb/dex2oat-boost/`。
> `pm.dexopt.*` 是**运行期属性**，**重启即回归系统默认**；不重启时卸载也会尝试还原。停用（不卸载）后重启即恢复原状。

### 方案 C · 已知未在真机验证的项

（来源：实施报告 §八 / §10.5，如实声明。）

1. **未做真机验证**，以下均需真机复核：
   - `resetprop -n` / `setprop` 对 `pm.dexopt.*` 的写入是否被 SELinux 放行；
   - 本机 KernelSU 的 `/data/adb/ksu/bin/resetprop` 是否存在可用；
   - `/data/app` 目录名形态（`~~<base64>==/<包名>-<hash>`）与「第一个 `-` 前为包名」是否成立；
   - `cmd package compile -m speed <包名>` 输出文本是否含 `Success`；
   - 并发编译是否真并行（PMS / installd 可能串行排队）；
   - 覆盖安装时 `pm path` 是否如期先指旧目录、后指新目录（就绪门禁依赖此行为）。
2. **未做真刷入**：纯 shell 模块无编译产物，zip 未在真机 Magisk/KSU 上实际刷过。
3. 依赖 KernelSU/Magisk 的 `service.sh` 开机执行机制；换 root 方案或 OTA 后可能需重新部署。
4. 本目标 ROM `pm.dexopt.install` 的默认值未知。

### 方案 C · 出问题先看哪里

1. `su -c 'cat /data/adb/dex2oat-boost/dex2oat-boost.log'` —— 守护主日志（属性写入、每个包的重编译 / 等待 / 重试 / 放弃）。
2. `su -c 'tail -n 50 /data/adb/dex2oat-boost/service.log'` —— 看门狗日志（守护是否起来 / 反复重启）。
3. `su -c 'cat /data/adb/dex2oat-boost/orig_props.txt'` —— 本次开机记录的原属性值。
4. `su -c 'cat /data/adb/dex2oat-boost/state.tsv'` —— 基线快照（判断某包是否被判为「新增」）。
5. 配置调整见 [`magisk模块/README.md`](magisk模块/README.md) §五（`config.prop`，改完**重启生效**）。

## 两条路共同的坑

- **先装模块 / 刷模块，再装测试包**——否则基线 / 降档窗口错过（方案 C 尤其明显）。
- 若两条路都启用：同一次安装会**重复编译一次**（无害但浪费），日志会看到两套；**建议只启一条**。
