# 相册内容分析控制 — 设计方案（草案）

作用域：`com.miui.gallery`。目标是在不影响相册白天既有行为的前提下，提供夜间自动分析 + 设置页手动控制。

分析依据见 [`_分析/report.md`](_分析/report.md)。

## 一、自动触发

| 项 | 决定 |
|---|---|
| 时间窗 | 20:00 — 次日 06:00 |
| 频率 | 每 30 分钟一次 |
| 约束 | 电量不低（不要求 idle） |
| 精度 | 不要求准时，允许被系统推迟 |
| 白天 | 不拦截相册自身的触发，照旧 |

实现方式：

- 在相册进程内另入队一个独立的 `PeriodicWorkRequest`（30 分钟），复用相册的 `CardUpdateWorker` 类，使用专属 unique name 与专属 tag
- **不修改**相册原有 `com.miui.gallery.job.CardUpdate` 任务，避免把白天触发一并删掉
- hook `CardUpdateWorker.doWork()`：带专属 tag 且当前时间不在窗口内 → 直接返回成功；其余情况原样放行

## 二、手动入口

hook `GallerySettingsFragment.onCreatePreferences`，在原逻辑执行后向 `findPreference("others")`（"其他设置"分类）追加**一行**：

- 行标题：AI 内容分析
- 行摘要（summary）：当前状态，空闲 / 分析中 / 正在停止，页面可见期间刷新
- 行右侧（widget 区域）：启动、停止两个按钮

实现：模块内定义一个 `Preference` 子类，在 `onBindViewHolder` 中向 `android.R.id.widget_frame` 动态添加两个按钮，每次绑定时按运行状态刷新文案与可用性。

行为：

- 启动：后台线程调用 `CardUpdateWorkerProvider$CardUpdateWorker$Companion.execDirectly(false, false, 4)`
- 停止：调用 `Companion.cancel("user_stop")`

约束：

- `execDirectly` 禁止在 UI 线程调用
- "其他设置"分类 key 找不到时整块不显示，不影响设置页
- `state=4` 会跳过充电/息屏/节流判断，同时不注册温度、拔电、亮屏的自动取消

## 三、停止与状态

- 06:00 到点不打断正在运行的分析，等其自然结束
- 状态判断：`Companion.isRunning()` 与静态字段 `mCanceled`
- 运行中重复点击启动会被 `isRunning` 自动挡掉

## 四、未决 / 未验证

- 设置页注入的视觉样式未在真机确认
- 夜间任务被 Doze 推迟的实际幅度未实测
- 相册进程被冻结或杀死时，入队任务能否按时恢复未实测
- 国行 aicr 已接管设备上，"触发"是否只触发拉取而非重新计算，仍未验证

### 5.2 与草案的一处实现差异

草案写的是「模块内自定义 `Preference` 子类」。实际未采用，原因：LSPosed 模块类由独立 ClassLoader 加载，模块内的类不能继承相册进程里的
`androidx.preference.Preference`（同名类在不同 ClassLoader 中不是同一个 Class，加入相册的 Preference 树会类型不匹配）。

实际做法（可见行为等价）：
- 用相册自己的 `androidx.preference.Preference` 类反射创建实例，设置 key/title/summary，`setPersistent(false)`，加入 `others` 分类；
- hook `androidx.preference.Preference.onBindViewHolder`，在绑定到本行时向 `android.R.id.widget_frame` 动态添加「启动」「停止」两个按钮；
- widget_frame 不可用 → itemView 上加一个按状态切换文案的单按钮；
- 再不可用 → 行点击切换（summary 提示「点按切换」）。
任何 UI 异常都只记日志，不影响设置页其他内容。

另一处按本机实际 API 做的兼容：相册 4.3.1.16 的 `androidx.work` 中 `ListenableWorker` 没有 `getParameters()`、`WorkerParameters` 没有 `getTags()`，实际是 public 字段 `mWorkerParams` / `mTags`（`_分析/jadx_out/sources/androidx/work/ListenableWorker.java:8`、`WorkerParameters.java:13`）。`TimeWindowHook` 先尝试 `getParameters().getTags()`，失败再读 `mWorkerParams.mTags`，两种版本都能工作。

8. 国行 aicr 已接管设备上，触发是否只拉取而非重新计算，仍未验证（同草案第四节）。

### 5.5 真机 1.0 反馈与修复（v1.1）

真机装 1.0 后三组 hook 均装载成功，但夜间任务入队失败：

```
NoSuchMethodError: androidx.work.PeriodicWorkRequest$Builder#setConstraints
```

原因：`XposedHelpers.findMethodExact` 只查本类声明的方法，而 `setConstraints` / `addTag` / `build` 都声明在父类
`androidx.work.WorkRequest$Builder` 上（`PeriodicWorkRequest.Builder` 只声明构造函数和
`buildInternal$work_runtime_release`）。同类问题还有设置页：`findPreference` / `addPreference` 声明在父类
`PreferenceFragmentCompat` / `PreferenceGroup`，`onResume` / `onPause` 声明在 `androidx.fragment.app.Fragment`
——1.0 的「其他设置」行实际上没有加进去。

修复：

- 新增 `hook/Reflect.java`：沿父类与接口向上查找方法；模块内反射调用统一改走它。
- `NightWorkScheduler`：三个方法改从父类解析；约束去掉 idle，只保留「电量不低」（Doze 空闲态要求未充电，充电过夜永远不满足）。
- `SettingsHook`：`findPreference` / `addPreference` 沿父类解析；行对象改用 `miuix.preference.BasePreference`（不可用时退回 `androidx.preference.Preference`）；`onResume` / `onPause` 在声明处 hook，回调内按实例类型过滤。

### 5.7 放宽电源门禁（v1.3）

需求：充电与高电量满足其一即可跑；手动启动不受亮屏限制。

- **手动启动**本来就跳过亮屏检测：`execDirectly` 里 `z7 = startState != 0`，state=4 直接越过充电与息屏两个判断，也不注册温度/拔电/亮屏的自动取消。本版无需改动。
- **自动触发**原先硬性要求充电（`!z7 && !getIsPlugged() → return`）。新增 `PowerGateHook`：
  - hook `Companion.execDirectly` 的 before/after，在 `startState==0` 且未充电但电量 >92% 时，用 ThreadLocal 标记；
  - hook `GalleryPreferences$Sync.getIsPlugged`，仅在标记生效期间返回 true。
    不改偏好本身，云同步/下载等同样读该开关的逻辑不受影响。
  - 子任务的门禁是 `getPowerCanSync() || getIsPlugged()`，而未充电时 `getPowerCanSync()` 在电量 >20% 就为真，因此放行后子任务不会二次卡住。
- **充电广播**原先只在插电时判断「电量>92% + 温度<43℃ + 息屏」。新增对 `BatteryMonitor` 内部广播接收器 `onReceive` 的 hook：不插电、电量 >92%、温度 <43℃、屏幕熄灭时补调一次 `tryTriggerCalc(false)`。

自动路径仍保留 `ScreenMonitor`（亮屏即取消）与温度监听（≥43℃ 取消）；拔电监听只在「插着→拔掉」这一变化时取消，起始就不插电不影响执行。
