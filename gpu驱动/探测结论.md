## 结论 1：★ SELinux 放行规则**已经存在**，这条补丁不用做

```
[system_ext_sepolicy.cil] 1061:(type graphicsengine)
[system_ext_sepolicy.cil] 2285:(allow graphicsengine hwservicemanager_prop (file (read getattr map open)))
```

帖子要补的那条，**已经在你机器上**，而且位置完全符合博客 R2（域声明在 system_ext 组 → 规则也写 system_ext）。
dmesg 里 graphicsengine 相关 avc 拒绝 **0 条**。

→ **原方案的"核心项"是空的。** 不用做，做了只是重复。

### 顺带更正上一轮我的一个说法

`hwservicemanager_prop` 不是设备文件，是**属性类型**（property type）—— 对应 `/dev/__properties__/` 下的属性命名空间，实际管的是 `hwservicemanager.ready` 这类属性。

证据：日志里 `(allow hwservicemanager hwservicemanager_prop (property_service (set)))` —— class 是 `property_service`。所以 `(file (read getattr map open))` 是"**读属性**"的权限集合，不是"读文件"。这也解释了为什么 F 段在 `/dev/` 下找不到 `hwservicemanager_prop` —— 本来就不该在那。

### 另一个观察：precompiled_sepolicy 在 /odm

G 段查的三个路径都没有，但 E 段列 `/odm/etc/selinux/` 时明确有 `precompiled_sepolicy`（外加三个 `.sha256` 校验文件）。
对**离线改 .cil** 的路线这很重要（改文本 .cil 可能不生效，得同步重建 precompiled）；对**运行时打策略补丁**（Magisk/KernelSU）不影响。我们走后者，无需处理。

## 结论 2：★ 预热缓存仍然是 0，但**原因不是 SELinux**

```
[5] 预热缓存目录数 : 0    （0 = 预热没跑起来）
/data/system/graphicsengine/  → total 0（目录在，空）
```

服务在（`/system/bin/graphicsengine` + `graphicsengine.rc`）、SELinux 规则在、avc 也没有 —— 那失败点就在别处。

**最可疑的嫌疑**：`persist.sys.enhance_vkpipelinecache.enable` **没设**。博客 F2 说这条是预热总开关（服务、libEGL、libhwui 三方都读）。你的 `system.prop` 里没有它，ROM 里也没查到设置。

（这是**推测**，不是结论。目录存在说明服务至少跑过、建了目录。）

### 下一步取证命令（一条，决定性）

博客 F3 说预热门失败时二进制会打印 `ARCHI_PipelineCache, vulkan environment not ready`。直接翻 logcat：

```
su -c 'logcat -d | grep -iE "ARCHI_PipelineCache|graphicsengine" | tail -50'
```

- 有 `vulkan environment not ready` → 预热确实被挡在门外，继续查为什么
- 什么都没有 → 服务根本没起来，或者起来就静默退出了，方向要换

## 结论 3：抢占节点可做

```
-rw-r--r-- root root u:object_r:vendor_sysfs_kgsl:s0  /sys/class/kgsl/kgsl-3d0/preemption
当前值: 1
init.qcom.post_boot.sh 尾部 25 行 → 没有任何抢占补丁
```

节点在、类型是 `vendor_sysfs_kgsl`（与博客 F4 吻合）、当前值 1（抢占开着）。

原帖补丁是追加到 `/vendor/bin/init.qcom.post_boot.sh` —— 那是 ROM 分区文件，模块要改得整份 overlay，ROM 一更新就失效。
**改走模块的 `service.sh`**：等 `sys.boot_completed=1` 之后再写，才能保证是最后一次写入。

### 先验证写权限（5 秒，只影响本次开机，重启恢复）

```
su -c 'echo 0 > /sys/class/kgsl/kgsl-3d0/preemption; cat /sys/class/kgsl/kgsl-3d0/preemption'
```

打印 `0` = KernelSU 的 su 域对该节点有 write，`service.sh` 方案可行。
打印 `1` 或 Permission denied = 需要另想办法（策略放行），先别做。

## 结论 4：KernelSU 影响模块设计

没有 Magisk，所以 **Magisk 的 `sepolicy.rule` 机制不适用**（好在 SELinux 那项本来也不用做）。
`/data/adb/ksu/bin/` 里**没有 magiskpolicy**，KernelSU 下没法直接命令行打策略补丁。

模块可用钩子：`module.prop`、`system/`（overlay）、`system.prop`、`post-fs-data.sh`、`service.sh`。
已装 `meta-overlayfs`（MetaModule），overlay 机制正常。
