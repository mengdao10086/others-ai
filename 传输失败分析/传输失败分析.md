# LocalSend `[500] Could not save file` 原因分析报告

- 分析日期：2026-10-31
- 样本：`D:\下载\LocalSend\base-3.apk`
- 一句话结论：**接收端 LocalSend 在保存文件时，直接把发送端传来的原始文件名拼进目标路径，没有做非法字符清洗；LSPosed 日志名里的时间戳含两个 `:`，被接收端操作系统/文件系统拒绝，保存抛异常，服务端返回 HTTP 500 `Could not save file`，发送端再把它格式化成 `[500] Could not save file`。**

## 2. 应用结构：业务逻辑全在 Dart AOT 里，不在 Java/smali

- 这是 Flutter 应用。Java/DEX 层只有壳：`org/localsend/localsend_app/MainActivity.smali` 继承 `io/flutter/embedding/android/d`（FlutterActivity），没有 `configureFlutterEngine`、没有自定义 MethodChannel。
- 全量 smali 中**搜不到** `Could not save file`；该字符串只存在于 `lib/<abi>/libapp.so`（Dart AOT 快照）。
  - arm64-v8a：文件偏移 `872524`
  - armeabi-v7a：文件偏移 `4298660`
  - x86_64：文件偏移 `872540`
- 因此本报告的业务代码证据使用与 APK 版本完全对应的上游 v1.14.0 源码；由于 APK 与官方 release 哈希一致，源码与二进制可视为同一构建产物。Dart AOT 本身未反编译成可读伪代码（本机无 Dart AOT 反编译器，且任务禁止新装工具）。

## 3. `[500] Could not save file` 的产生链路

### 3.1 发送端：`[500] …` 的格式化位置

发送端收到接收端的 HTTP 错误后，用扩展方法 `humanErrorMessage` 拼消息。

`app/lib/provider/network/send_provider.dart`（v1.14.0）

```dart
// 443-454 行
String get humanErrorMessage {
  final e = this;
  if (e is DioException && e.response != null) {
    final body = e.response!.data;
    String message;
    try {
      message = (body as Map)['message'];
    } catch (_) {
      message = body;
    }
    return '[${e.response!.statusCode}] $message';
  }
  return e.toString();
}
```

接收端返回 JSON `{"message":"Could not save file"}`、状态码 500，于是发送端显示 `[500] Could not save file`。

### 3.2 接收端：500 的返回点


## 4. 为什么这个 LSPosed 日志“必然”失败

失败文件名（发送端原样传输）：

```
modules_2026-10-30T21:11:49.815775.log
                    ↑  ↑
```

里面包含 **两个 `:`**（ISO-8601 时间戳）。

保存路径在接收端变成（以 Android 默认目录为例）：

```
/storage/emulated/0/Download/modules_2026-10-30T21:11:49.815775.log
```

各平台对该文件名的接受情况：

| 接收端 | 结果 | 依据 |
|---|---|---|
| Android 11+（公共存储，本 App 默认 Download 目录） | **拒绝**：`open failed: EPERM (Operation not permitted)` | 上游 issue #1063（`PathAccessException ... my:cool:video.mp4 ... errno = 1`）、#1101（Android 13 对 FAT32 非法字符一律 500）；Android 11+ 公共存储对 `:` 等字符返回 EPERM（多处 Android 开发社区实测） |
| Windows（NTFS） | **拒绝**：`:` 是 Win32 文件名非法字符 | Windows 文件名规则 |
| FAT32 / exFAT（外置 SD 卡等） | **拒绝**：`:` 属 FAT 非法字符 | FAT32 规范；上游 #1101 实测 |
| Linux（ext4 等） | 允许 | 上游 #1063 发送端 Linux 可建同名文件 |
| macOS/iOS | 未验证（见第 6 节） | — |

所以：**LSPosed 的 module 日志名统一是 `modules_<ISO时间戳>.log`，每个都带 `:`；只要接收端是 Android 11+ 公共存储、Windows 或 FAT32/exFAT，这个文件就必然命中 500。** 不带冒号的日志（如 `modules.log`、`verbose.log`）不会因此失败。

需要强调：真正返回 500 的是**接收端**的 LocalSend 实例（PC 或另一台手机），本 APK 里的是同一套 Dart 代码；发送端只负责把文件名原样发出并显示 `[500] …`。

## 5. 一般化失败判据

### 5.1 决定性因素：**文件名中的字符集**（相对接收端的文件系统）

| 因素 | 是否在起作用 | 说明 |
|---|---|---|
| 文件名 | **是（本案唯一决定因素）** | 含接收端文件系统不允许的字符 → `openWrite()` 抛异常 → 500 |
| 扩展名 | 否 | `.log` 只影响 `guessFileType()` 归类为 `other`，不参与保存路径合法性 |
| 完整路径 | 间接 | 默认落在 `/storage/emulated/0/Download/`（公共存储）；路径本身合法，非法的是文件名 |
| MIME | 否 | `lookupMime()` 只用于协议描述，不影响保存 |
| 大小 | 否 | 本代码是流式写入，1.5 MB 级别无任何限制；本案与大小无关 |
| 权限 | 另一类 500 原因 | 未授予 MANAGE_EXTERNAL_STORAGE、目标目录不可写等，会造成同一条 500，但与“某些文件失败、某些成功”的规律无关 |
| 存储分区 | 相关 | 外置 exFAT/FAT32 比内部公共存储更严格，但规则同为“按 FAT 字符集拒绝” |

**可复现的失败字符清单（按接收端类型）**

- Windows：`\ / : * ? " < > |`，控制字符，保留设备名（`CON`、`PRN`、`AUX`、`NUL`、`COM1-9`、`LPT1-9`），结尾的 `.` 或空格。
- Android 11+ 公共存储 / FAT32 / exFAT：至少 `: * ? " < > | / \`；上游 issue #1101 实测 Android 13 上 `* / : < > ? \ | + ; = []` 均会 500。
- 文件名组件超过 255 字节、整路径超过约 4096 字节（各 FS 不同）：同样在 `openWrite`/`createSync` 失败。
- Linux/macOS：上述多半允许（macOS 的 `:` 在 POSIX 层合法，Finder 显示为 `/`）。

### 5.2 同一条 500 的其它触发点（非本案）

- 接收目录不存在且无法创建：上游 issue #252/#266（`/storage/emulated/0/Download` 被删）。
- 没有存储权限 / 自定义目标目录不可写（Android 11+ 未授权 `MANAGE_EXTERNAL_STORAGE`）。
- 磁盘满、只读分区。
- 图片/视频且开启“保存到相册”时，`Gal.putImage/putVideo` 失败。
- 保存过程中会话状态变化：`receive_controller.dart:421` `responseJson(500, message: 'Server is in invalid state')`（注意文案不同，不是本例）。

## 6. 正常文件对照

| 文件名 | 结果 |
|---|---|
| `modules_2026-10-30T21:11:49.815775.log` | **失败**（含 2 个 `:`) |
| `modules_2026-10-30T21-11-49.815775.log` | 成功（字符集合法，走同一段代码） |
| `modules_2026-10-30T21.11.49.815775.log` | 成功 |
| `modules.log` | 成功 |

代码层面二者的唯一差别就是 `destinationPath` 字符串；`file_saver.dart` 的保存流程、扩展名判断、MIME、大小处理完全相同。

## 7. 解决方案（可直接照做）

### 方案 A：发送前把文件名改合法（最快，推荐）

在手机（发送端）上复制一份并改掉冒号，再发送副本：

```bash
# root shell（LSPosed 日志在 /data/adb，需要 root）
cp "/data/adb/lspd/log/modules_2026-10-30T21:11:49.815775.log" \
   "/sdcard/Download/modules_2026-10-30T21-11-49.815775.log"
# 然后在 LocalSend 里选 /sdcard/Download/modules_2026-10-30T21-11-49.815775.log
```

无 root 时用能读该路径的文件管理器（如 MT 管理器）另存为不含 `:` 的名字。
也可先打包成 zip 再发（zip 文件名本身合法）；但 zip 内条目名仍带 `:`，Windows 解压时可能被改名，不如直接重命名可靠。

### 方案 B：接收端在接收页面改名（无需改文件）

接收端 LocalSend 1.14.0 默认“快速保存”关闭（`persistence_provider.dart:279-280` 默认 `false`），收到请求时会弹出接收页：

1. 点文件名右侧铅笔图标（`receive_options_page.dart:161-167` → `FileNameInputDialog`）；
2. 把 `:` 改成 `-` 或 `_`；
3. 再点接收。

> 若接收端开了“快速保存（Quick Save）”，会跳过改名界面直接保存 → 必然 500。先关闭该设置。

### 方案 C：升级接收端 LocalSend

v1.18.2 已内置文件名清洗：`packages/localsend_isolates/lib/src/task/server/file_saver.dart:167-193` 的 `sanitizeRelativeName()` 对每个路径组件调用 `rust_filename.sanitizeFileName()`，保存前自动替换非法字符；改名对话框也加了校验（`file_name_input_dialog.dart:31-41`）。

- 只需升级**接收端**（PC 或另一台手机）；发送端 1.14.0 不用动。
- 代价：文件名会被自动改写，需要在接收端核对实际保存名。
- 未逐一核对从哪个版本开始引入，仅确认 1.18.2 已具备。

### 方案 D：改源码（需要重编译，不是改 smali）

逻辑在 Dart AOT，改 smali 无效。基于 v1.14.0 源码改：

1. `app/lib/util/native/file_saver.dart` 的 `digestFilePathAndPrepareDirectory`：
   ```dart
   // 原：final actualFileName = p.basename(fileName);
   final actualFileName = p.basename(fileName)
       .replaceAll(RegExp(r'[\\/:*?"<>|]'), '_');
   ```
2. 同步在 `app/lib/widget/dialogs/file_name_input_dialog.dart` 的 `_submit()` 做同样替换/校验，避免用户手动改名再次踩坑。
3. 用 Flutter 重新构建 APK（v1.14.0 对应 Flutter 版本），签名安装。
4. 上游参考：PR #1336（`legalize` 包方案，未合并）；1.18.2 已改用 `rust_filename.sanitizeFileName`，可照搬其规则。

### 不建议/无效的做法

- 改扩展名、改 MIME、压缩体积：对本案无效。
- 在 1.14.0 的设置里找不到“自动清洗文件名”选项：该版本没有此功能。
